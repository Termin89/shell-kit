# Модуль (module)

Слой контрактов для авторов модулей. Если `src/core` — то, как shell видит
модули (реестр, активация, загрузка), а `src/react` — как их рендерить,
то `src/module` — то, **что такое модуль изнутри** и из чего он собирается.

## Определение

**Модуль — независимое полноценное мини-приложение.** Приложение — набор
модулей, собранных shell'ом. Модуль строится по классическому MVC:

| Часть | Роль MVC | Что это |
| --- | --- | --- |
| `service` | модель | доменный сервис модуля: регистрация `{ id, instance }` (обычно диспетчер `defineService`); instance получает контроллер, id — для shell-инфраструктуры (mock-service, логи) |
| `PageController` | контроллер | подключает сервис (аргументом от модуля) и shell-состояние, отдаёт пропсы для вьюхи (кастомный хук `useXxxProps`) |
| `PageComponent` | представление | чистая вьюха без бизнес-привязок, собрана из компонентов общей библиотеки и виджетов, покрыта семантическими токенами (design system) |

Страница (`page`) = `PageController` + `PageComponent`. Собранные вместе
страница и сервисы дают **контракт модуля** — `ShellModule`:

```ts
interface ShellModule<P> {
  view: ComponentType;        // конечная собранная вьюха — её рендерит ModuleRenderer
  component?: PageComponent<P>; // чистая вьюха — частичное использование модуля
  service?: ModuleService;    // сервисы — для самого модуля и shell-инфраструктуры
}
```

`defineModule` собирает контракт из частей:

```tsx
import { defineModule } from "@/module";
import CatalogPage from "./CatalogPage";
import { useCatalogProps } from "./controller";
import { catalogService } from "./service";

export default defineModule({
  page: {
    component: CatalogPage,      // чистая вьюха на пропсах
    controller: useCatalogProps, // (service: CatalogService) => Props
  },
  service: { id: "catalog", instance: catalogService },
});
```

Сервис передаётся контроллеру аргументом, а не из замыкания: связка
«контроллер ↔ сервис» декларативна (видна в module.ts) и проверяется
типами — контроллер, требующий сервис, без регистрации не соберётся.
Модуль без сервиса объявляет контроллер без параметров.

Файл модуля (`load()` из `ModuleConfig`) резолвится адаптером: приоритет —
`default.view` (контракт ShellModule), затем прежние формы (`default`,
`Component`, сам модуль-функция).

### Зачем defineModule

Сегодня фабрика механически проста (вызвать контроллер, прокинуть пропсы)
— её ценность в другом:

- **единая форма** — все модули собираются одинаково: нельзя забыть
  обёртку или изобрести свою структуру экспорта; контракт всегда содержит
  `view` и `component`;
- **инъекция сервиса** — контроллер получает сервис аргументом от
  модуля, а не из замыкания: замена сервиса (другой диспетчер,
  тестовый дубль) — точечная правка module.ts;
- **данные для инфраструктуры** — опции (`page`, `service`) декларативны,
  их потом прочитают mock-service и реестр модулей.

### view и component — в чём разница

Разные потребители — разные экспорты:

| | `component` | `view` |
| --- | --- | --- |
| Что это | чистая вьюха | component + применённый контроллер |
| Вход | props | без пропсов |
| Кому нужен | другой композиции: другой дизайн, свой контроллер, сторибук | рендереру |
| Аналогия | `Component` | `connect(Component)` |

`view` обязан быть без пропсов: рендерер не знает типов пропсов модуля —
их знает только контроллер. `component` остаётся для частичного
использования.

## Правила связей

- Модули **не связаны между собой** напрямую: ни импортами кода, ни
  обращением к сервисам соседа. Взаимодействие — только через shell
  (состояние, навигация, `loadModule`).
- Если два модуля скрещены связями — это уже один модуль. Граница модуля
  проводится по связности: всё, что сильно связано, живёт внутри.
- «Подмодули» внутри модуля — та же мерка: экран, делящий с соседями
  сервис/сессию/запросы, — часть одного модуля (его вьюха-подстраница);
  отдельный модуль — только когда связь действительно ушла (свой сервис,
  нет общего стейта).
- Следствие: модули можно добавлять, изменять и удалять, зная, что это
  не влияет на сложность и связи остальных. По набору модулей видно,
  какие части приложения готовы, а какие предстоит сделать.

## Зачем выносить части отдельно

Разделение `component` / `controller` даёт **частичное использование**
модуля:

- чистую вьюху можно встроить в другую композицию, подставив свой
  контроллер (другой источник данных, другой scope);
- контроллер можно переиспользовать с другой вьюхой (та же бизнес-логика,
  другой дизайн — быстрая смена верстки под готовые системы);
- `view` — то, что обычно нужно рендереру: модуль «как есть».

## Что дальше (расширение контракта)

Регистрация `service` (`{ id, instance }`) и проброс instance в
контроллер — реализованы. Точки роста вокруг них, по заметкам архитектуры:

- **api-client** — клиент с ручками;
- **конфиг сервиса** — точка входа baseUrl, интерсепторы, обработчики
  ошибок, автогенерация хуков из ручек;
- **mock-service** — подключает сервисы и переключает режим (живой API /
  мок) в рантайме; своя вьюха, где по каждому сервису можно включить мок
  или выбрать seed.

Обсуждалось и отложено: **подстраницы на уровне контракта** (`routes` в
`defineModule`, чтобы модуль декларировал свои экраны таблицей, а не
резолвил хвост руками). Осознанно не делается: экраны модуля делят одно
дерево хуков — общие запросы, фильтры, SWR-стэш, свап-поверхность; таблица
маршрутов на уровне контракта подталкивает к отдельным вьюхам на маршрут
и дерево рвёт. Канон больших модулей — тонкий контроллер-корень + слайсы
на экран (`controllers/<экран>.ts`), маршрутизация остаётся внутри модуля
(эталон — feed в u-kon).
