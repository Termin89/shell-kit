# Концепция состояния Shell

`AppState` — это не «стейт всего приложения», а **контекст сессии**, из
которого ядро выводит конфигурацию системы модулей. Единственный вычислитель
от state внутри ядра — активация: `enabled(state)`. Все остальные потребители
(UI, модули, мосты в стейт-библиотеки) читают state, но не являются причиной
его изменений.

## Задача

Хранить самые общие данные, одинаковые для всего приложения и влияющие на
то, **какие модули активны**:

| Категория | Примеры |
|---|---|
| Идентичность и права | `user`, `roles`, `permissions`, `scope`, тенант |
| Окружение | `locale`, `theme`, `env` (dev/prod), платформа |
| Конфигурация запуска | feature flags, режим моков |

Практическое правило: **если значение влияет на набор активных модулей —
оно должно лежать в Shell state. Если не влияет — не должно.**

Отдельно от активации в базовом `AppState` живёт обязательное поле
`activeModule: string | null` — выбранный для отображения модуль. Оно
**не влияет на активацию**: видимость (какие модули существуют в текущем
контексте) и выбор (какой из них показывать) — разные вопросы. Ядро поле
не интерпретирует — только несёт через состояние, чтобы выбор был виден
любому подписчику; пишет его типизированный метод `shell.setActiveModule(id)`
(union id выводится из конфига модулей, в рантайме id проверяется
по реестру).

## Что state НЕ делает (non-goals)

- **Не хранит бизнес-данные модулей.** Каталог, корзина, лента — это данные
  модулей (серверный кеш — React Query/SWR и т.п., формы — свои решения).
  Shell не является ни кешем сервера, ни хранилищем доменных сущностей.
- **Не хранит высокочастотные значения**: таймеры, позиция ввода, координаты
  курсора. Каждое изменение state пересчитывает активацию модулей — state
  должен меняться редко (вход/выход, смена языка/темы/прав).
- **Не является event bus'ом.** Обмен сообщениями между модулями — отдельный
  механизм (в планах ядра).
- **Не содержит маршрут.** Роутинга в ядре нет: путь/URL — вообще не
  забота ядра. Какой модуль показывать — решает layout, читая
  `activeModule` и свой fallback; ядро только несёт это поле
  через состояние.
- **Не содержит несериализуемое**: инстансы классов, DOM-ссылки, функции.
- **Не предоставляет селекторы/вычисления.** Ядро отдаёт state целиком;
  мемоизация и производные значения (`isAuthenticated` и т.п.) — уровень
  адаптеров и приложения.

## Инварианты (свойства, на которые можно полагаться)

1. **Сериализуемость.** State — plain JSON-объект. Это даёт SSR-гидрацию,
   персистентность сессии, отладку и логирование из коробки.
2. **Иммутабельность ссылок.** Каждый `setState` производит новую ссылку
   на state. На этом держатся `useSyncExternalStore` в адаптерах и любые
   мосты: сравнение по `===` всегда корректно.
3. **Редкость изменений.** Изменение state = пересчёт активации всех
   модулей + уведомления. Это архитектурная цена, поэтому state меняют
   только для событийно значимых переходов (смена пользователя, scope).
4. **Одноуровневые обновления.** `Partial<S>` верхнего уровня или функция
   `(s) => s` для сложных случаев. Вложенные патчи не поддерживаются —
   сложные переходы пишутся функцией.
5. **Синхронные уведомления.** Подписчики вызываются синхронно внутри
   `setState`. Порядок: обновление state → слушатели `subscribe` →
   пересчёт активации (`onModuleChange` при изменении набора).
6. **Минимальный контракт стора.** `getState` / `setState` / `subscribe` —
   это ровно контракт внешнего стора (тот же интерфейс, что у vanilla-стора
   zustand). Любая интеграция сводится к подписке, копировать данные не нужно.

## Типизация и расширение

Базовый контракт ядра — минимальный `AppState` (`activeModule`). Приложение
расширяет его, не меняя ядро. Два механизма, работают вместе:

**1. Дженерики (основной способ).** `Shell<S extends AppState = AppState>`
типизирует `getState` / `setState` / `subscribe` / `enabled` под состояние
конкретного приложения:

```ts
interface AppShellState extends AppState {
  user: User | null;
  locale: "ru" | "en";
}

const modules = [
  {
    id: "admin",
    load: () => import("./modules/admin"),
    enabled: (s) => s.user?.roles.includes("admin") ?? false, // s типизирован
  },
] as const satisfies readonly ModuleConfig<AppShellState>[];

const shell = new Shell<AppShellState, typeof modules>({
  initialState: { activeModule: null, user: null, locale: "ru" },
  modules,
});

shell.setActiveModule("admin"); // id типизированы конфигом модулей
```

**2. Declaration merging (альтернатива).** Приложение дополняет
`AppState` глобально — удобно для небольших приложений без дженериков.

Для React-адаптера типизация доезжает через тонкую обёртку в приложении
(контекст держит базовый `Shell`, приложение сужает тип один раз):

```ts
// app/shell.ts — единственное место, знающее AppShellState
export const useAppShellState = () => useShellState() as AppShellState;
```

Ядро обязуется не расширять `AppState` полями, не нужными для активации
модулей, — чтобы не конфликтовать с полями приложений.

## Переиспользование в стейт-библиотеках (zustand, jotai, ...)

State ядра уже совместим с контрактом внешнего стора, поэтому мосты —
это подписка, а не синхронизация копий:

- **zustand**: компонент может читать Shell state напрямую через
  `useShellState()` рядом с zustand-стором модуля; либо обернуть в
  vanilla-мост `shell.subscribe` — данные не дублируются.
- **jotai**: атом-обёртка — read через `shell.getState()` + подписка на
  `shell.subscribe`, write — `shell.setState`.
- **Разделение ответственности**: Shell state — контекст сессии
  (активация, права, окружение); стейт-библиотеки — данные модулей.
  Смешивать их в одном хранилище — антипаттерн: это ломает инвариант
  редкости изменений Shell state.

## Открытые вопросы

- Порядок уведомлений в `setState`: сейчас слушатели состояния срабатывают
  до пересчёта активации — возможно, логичнее пересчитывать активацию до
  уведомлений.
- Dev-режим валидации state: проверка сериализуемости и неизвестных ключей
  (только в development-сборке).
- Персистентность и гидрация (SSR) — кандидат в плагины, не в ядро.
