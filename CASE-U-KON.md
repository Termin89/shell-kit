# Кейс U-kon: что даёт shell-kit этому проекту

Разбор ТЗ первой итерации «Клуб U-kon» (frontend поверх SmartyPro) и
статического прототипа (`u-kon/prototype`: index.html + app.css + app.js —
все экраны застимованы) с позиции shell-kit: **как быстрее построить**,
**какие риски снимает**, **что переиспользуется дальше** и **почему это
выгоднее, чем «LLM с нуля при готовом API»**.

Сводка по ТЗ: 25 экранов/состояний, 5 ролей, ~24 бизнес-сущности,
REST + WebSocket, обязательные стейты loading/empty/error/access denied
на каждом экране, code splitting и кеширование — требования
производительности зафиксированы контрактом.

---

## 1. Карта: экраны ТЗ → модули shell-kit

Граница модуля = домен + владение. Детальные страницы живут внутри
модуля своего домена (не отдельные записи реестра).

| № ТЗ | Экраны | Модуль | Природа |
|---|---|---|---|
| 1–3 | вход, регистрация, ожидание модерации | `auth` | **пресет** — готов в практике `services-auth`: SessionService (mock/api), статусные экраны через состояние |
| 4 | onboarding | фича layout'а | статика + флаг в состоянии |
| 5–6 | лента, детальная публикация | `feed` | **пресет** «лента + детальная»: query + фильтры + карточка |
| 7 | мессенджер | `messenger` | доменный: WebSocket, история, вложения — каркас из прототипа |
| 8–10 | создание (wizard), список, карточка запроса | `requests` | доменный: 3-шаговый wizard, статусы, история, отклики |
| 11–13 | каталог (карточки/список), карточка партнёра | `partners` | **пресет** «каталог в двух режимах»: режимы = `variants` одного контроллера, фильтры/поиск не сбрасываются — состояние модуля |
| 14–15 | ресурсы, карточка | `resources` | **пресет** «каталог» (тот же шаблон, другой тип сущности) |
| 16–17 | афиша, карточка, регистрация | `events` | **пресет** «каталог + запись» |
| 18 | профиль | `profile` | **пресет** |
| 19–20 | о клубе, тарифы | `about`, `tariffs` | статика; тарифы — из API (§38: не зашивать в код) |
| 21–22 | настройки, поддержка | `settings`, `support` | **пресет**; поддержка = вход в чат мессенджера |
| 23 | уведомления | `notifications` | общий UI поверх событий |
| 24–25 | модальные окна, стейты экранов | системное | **из коробки**: ModuleRenderer, query-стейты, error boundary + retry |

Итог: ~14 модулей, из них **7–9 — переиспользуемые пресеты**, 2–3
доменно-кастомных (мессенджер, wizard запросов), остальное — статика
на конфигурации. Роли (участник/партнёр/менеджер/админ/поддержка) —
`enabled`-предикаты + права в состоянии (порт computePermissions): одна
точка видимости вместо if'ов по всем экранам.

## 2. Как это ускоряет постройку

1. **Сквозное уже написано.** Transport-конверт, классификация ошибок,
   шина (тосты/retry), query-кеш с дедупликацией и инвалидацией, моки
   per-service с переключением на лету, ленивые чанки, error boundary —
   слои, которые при постройке «с нуля» пишутся заново каждый проект.
2. **Прототип → модули — механическая конверсия.** Прототип уже содержит
   вёрстку всех экранов и данные: каждая секция HTML становится чистой
   вьюхой модуля (`component`), данные прототипа — mock-стратегией,
   навигация прототипа (`showView`) — реестром модулей. Вёрстку не
   проектируем — переносим.
3. **API есть (SmartyPro) — но контракт уточняется.** Интерфейс сервиса
   описывается заранее, mock-стратегия работает до готовности ручек;
   переключение mock→api на лету — фронт и бэк не блокируют друг друга.
   Диспетчер per-call: интеграционные правки не пересоздают сервисы.
4. **WebSocket — на своём месте.** Ядро про realtime не знает (граница
   честно зафиксирована); событие WS → `invalidate(prefix)` query-порта —
   существующие экраны перечитывают данные без специальной логики.
5. **Требования §10 зарабатываются архитектурой, а не слежкой**:
   code splitting = `load: () => import()` у каждого модуля; кеш и
   дедупликация = query-порт; «не блокировать интерфейс» — Suspense и
   изоляция модулей.

## 3. Риски, которые снимает система

| Риск проекта | Без системы | Механизм shell-kit |
|---|---|---|
| Разношёрстность 25 экранов (у каждого свой подход к данным/ошибкам) | ревью каждого экрана заново, рефакторинги «приведения к общему» | контракты `defineModule`/`defineService`: все экраны одной формы, ревью по чек-листу |
| Стейты §48 (loading/empty/error/access denied) «где-то есть, где-то нет» | самое частое замечание приёмки | стейты встроены в слои: query-хук, рендерер, классификатор; access denied = notFound по `enabled` |
| Обработка ошибок зависит от исполнителя | кто-то alert'ит, кто-то глотает | единый конвейер TransportError → classify → шина → хендлеры; retry не пишется руками |
| Права/роли рисуются кнопками по всему коду | при смене роли — вычитка всего фронтенда | `enabled(state)` — одна точка; смена роли пересобирает навигацию сама (защита при этом остаётся на бэке, §13 — фронт только UX) |
| Лишние/дублирующиеся запросы при 100–200 rps | ручной кеш, гонки, повторные заходы | дедупликация и кеш query-порта, инвалидация по префиксу |
| Смена дизайна заказчиком (закрытый клуб, вкусовые правки) | правки логики экрана | controller/component split: диф не выходит за вьюху; второй режим каталога = `variants`, а не копия модуля |
| Работа нескольких исполнителей/агентов параллельно | конфликты в общем коде | модуль = папка, связи между модулями запрещены контрактно; реестр — по одной строке на модуль |
| Залипание на неготовности API | очереди «фронт после бэка» | моки per-service: фронт демонстрируем на моках, переключаем без перезагрузки |
| Потеря инвестиций в каркас (§52–55: frontend уходит заказчику) | весь сквозной код передаётся и остаётся в проекте | сквозное живёт в shell-kit — **универсальной библиотеке Исполнителя**, которая по §54 («ранее созданные библиотеки», «универсальные модули») не передаётся и работает в следующем проекте |

## 4. Переиспользование и экономика

**Этот проект — не только заказ, но и пополнение библиотеки.** Часть
модулей после U-kon становится пресетами shell-kit:

- `auth` (вход/регистрация/модерация) — уже есть (практика services-auth);
- «каталог в двух режимах» (партнёры) — та же форма закрывает ресурсы
  и афишу, а вне U-kon — любой справочник B2B-платформы;
- «лента + детальная», «профиль + приватность», «настройки»,
  «уведомления» — каркасы любого сообщества/SaaS;
- доменные (мессенджер, wizard запросов) остаются в проекте, но их
  контроллеры и сервисы тоже пишутся по контрактам — форма та же.

Экономика складывается из трёх эффектов:

1. **Внутри проекта.** Доля кода «по шаблону» (сквозные слои + пресеты +
   генерация) закрывает большую часть экранов; кастомными остаются
   доменные wizard'ы и мессенджер. Стоимость итераций (новый экран,
   редизайн, смена источника) падает кратно: решения приняты и закодированы.
2. **Между проектами.** Каждый следующий проект SmartyPro (и не только —
   стек универсален: любой REST API) стартует с пресетов: авторизация,
   каталог, лента, профиль. Кривая «стоимость N-го проекта» падает;
   U-kon — первая точка на ней.
3. **Правовая.** §52–55 ТЗ прямо разводит «индивидуальный frontend»
   (передаётся) и «универсальные компоненты/библиотеки Исполнителя»
   (не передаются). shell-kit — актив второй категории: инвестиция
   в каркас не уходит с проектом, а капитализируется в библиотеке.

## 5. Сценарий «LLM с нуля, есть только API»

Что происходит без системы: агент получает API и свободно проектирует —
управление состоянием, кеширование, обработку ошибок, структуру экранов
он **изобретает на каждом проекте**, и каждый раз немного по-разному.
Итог: непредсказуемое качество, дорогое ревью (каждый файл — новая
архитектура), §48-стейты по факту, а не по системе.

С shell-kit агент получает **форму вместо свободы**:

| Что нужно агенту | Откуда |
|---|---|
| как устроен экран | контракт `defineModule` + образцы (демо, практики) |
| как ходить в API | интерфейс сервиса руками → диспетчер; (этап C) endpoint-map из OpenAPI — ТЗ §7 требует описываемости в OpenAPI |
| как назвать хуки | конвенции + (этап E) кодеген из интерфейса: `get*/list*` → query, остальное mutation |
| что делать с ошибками | конвейер ошибок уже существует — агент его не пишет |
| как выглядит экран | прототип U-kon: секция HTML → чистая вьюха, конверсия механическая |
| где права и статусы | `enabled` + состояние; статусы аккаунта (§15) = ветки shell-состояния |

Проверка качества вырождается в чек-лист: типы собрались, линт зелёный,
контракт модуля соблюдён, мок-стратегия на месте. Ревью смотрит домен,
а не каркас. Это и есть разница: **LLM заполняет форму, архитектуру
не генерирует** — архитектура оплачена один раз, в библиотеке.

## 6. Честные границы

- Мессенджер (WS, синхронизация, вложения) — доменная работа; shell-kit
  даёт каркас модуля и интеграцию с кешем, не реализацию чата.
- Админ-модерация — по ТЗ средствами SmartyPro, фронт не строим.
- React Context из §6 стека: состояние shell через useSyncExternalStore
  совместимо (мост документирован в core/state.md), противоречия нет.
- Tailwind — не конфликтует: вьюхи чистые, стили любые.
- Нагрузочное тестирование (§11) — бэкенд-тема; со стороны фронта
  требования §10 закрыты архитектурно.

## 7. Вывод

U-kon — идеальный первый полигон shell-kit: средний размер (14 модулей),
типовой набор доменов сообщества (совпадает с пресетами на 60–70 %),
готовый прототип как источник вьюх, готовый API как источник контрактов.
Проект получает скорость и предсказуемость; библиотека — обкатанные
пресеты, которые не передаются заказчику (§54) и работают в следующих
проектах. Даже при генерации всего кода LLM наличие системы меняет
режим: вместо «спроектируй архитектуру» — «заполни контракт», что
дешевле, проверяемее и безопаснее по цене ошибки.
