# shell-core — карта фреймворка (для Miro)

Дата: 2026-10-01. Источники: README.md, VALUE.md, PLAN.md, ISSUES.md,
`src/*` (index-файлы слоёв). Назначение: база для карты в Miro —
позиционирование, способности слоёв, чего нет и куда развивать.

---

## 0. Что это и зачем

**shell-core — отдельный фреймворк, не привязанный к проектам.**
Его работа — чтобы LLM по задаче с HTML-прототипом/ТЗ **быстро и дёшево**
собирал **рабочий MVP** — за счёт композиции и переиспользования типовых
вещей, а не проектирования с нуля.

**Цель: генерация целого проекта из HTML.** Фреймворк обеспечивает
конвейер, по которому статический HTML-прототип превращается в рабочее
приложение целиком — от токенов и UI-примитивов до модулей, сервисов
и персистентных моков. LLM не проектирует каркас — каркас уже есть,
LLM заполняет его доменом.

- **Контракты вместо импровизации.** Модуль, сервис, видимость — заполненные
  формы (`defineModule`, `defineService`, `enabled`). Агент не проектирует
  архитектуру — он заполняет шаблон; опечатку ловит компилятор, не ревью.
- **Композиция типового.** Всё сквозное — навигация/видимость, состояние,
  данные с моками, ошибки, запросы, медиа, UI-примитивы — уже написано.
  Проект отличается доменами и настройкой, а не каркасом.
- **Мок раньше API.** Диспетчер стратегий per-call: MVP работает без
  бэкенда, api-подключение подменяет мок позже без правки модулей.
- **Дешевизна генерации.** Суженное пространство решений = меньше токенов
  на «придумывание», меньше ошибок, ревью проверяет домен, а не каркас.
  Конвенции имён и эталонные примеры (demo/practice) — few-shot выборка.

**Граница фреймворка:** механизмы и контракты — да; домены, дизайн-токены,
вьюхи, бэкенды — нет. С 2026-09-30 — независимый публикуемый пакет
(v0.1.0, git-зависимость `github:Termin89/shell-kit#v0.1.0`);
проекты-потребители (u-kon, partner-portal) — отдельные репозитории.

**Конвейер «HTML-прототип → проект» (главный флоу для доски):**

```
HTML-прототип / ТЗ
   → токены + структурные классы UI (методика портинга прототипа)
   → UI-слой проекта: примитивы → shared-блоки → страницы
   → модули по контракту: контроллер (useXxxProps) + чистая вьюха
   → сервисы: интерфейс + персистентный мок → MVP работает сразу
   → позже: api-стратегия подменяет мок, вьюхи и контроллеры не меняются
```

## 1. Слои фреймворка (блоки для Miro)

| Слой | Способность | Ключевые экспорты | Зависит от |
|---|---|---|---|
| `core` | Headless-ядро Shell: реестр модулей, видимость, bootstrap, состояние | `Shell`, `AppState`, `ModuleConfig`, `ShellStatus` | — (zero-deps) |
| `module` | Контракт модуля | `defineModule` (component/variants + controller) | core (типы) |
| `react` | React-тулкит: провайдер, гейт, рендерер, хуки | `ShellProvider`, `ShellGate`, `ModuleRenderer`, `useShell*`, `useActiveModules`, `useMedia` | core, storage |
| `solid` | Solid 2-адаптер (зеркалит react, идномы Solid 2: getter-аргументы, аксессоры) | те же + router/queries-связки (`RouterProvider`, `usePath`, `useServiceQuery`) | core, router, queries, storage |
| `router` | Опциональная синхронизация activeModule ↔ URL: конвенция `/:module/*` (первый сегмент — shell, хвост — модуль), вкл/выкл из конфига приложения выбором адаптера истории | `RouterPort`, `connectRouter`, `useNavigate`, `useModuleRoute`, `matchPath` | core (только публичный API стора) |
| `service` | Данные per-call: диспетчер стратегий (mock/api) | `defineService`, `ResolveContext` | core (services-конфиг) |
| `transport` | HTTP-труба: конверт ответов, типизированные ошибки | `HttpTransport`, `TransportResponse`, `TransportError` | — |
| `errors` | Классификация ошибок + шина + хендлеры | `classifyError`, `errorBus`, auth/network/toast-хендлеры | — |
| `queries` | Query/mutation-слой: кеш, дедуп, инвалидация | `useServiceQuery`, `useServiceMutation`, `QueryPort`, `SelfRolledAdapter` | react |
| `storage` | Локальная персистентность: данные + медиа | `configureStorage`, `dataCollection`, `putMedia`/`seedMedia`, `resolveMediaUrl`, `clearStorage`, `PersistentMock` | — (browser API) |
| `ui` | Универсальные UI-примитивы на структурных классах | `cx`, `createIcon`, `Button/Card/Chip/…`, `components.css` | — (токены даёт проект) |
| learning: `demo` | Эталон — онбординг людей и few-shot для LLM; dogfood публичного API (импортирует пакет по имени) | демо-модуль на полном стеке | все слои |
| learning: `demo-solid` | Компактный эталон Solid-адаптера: lazy/retry/loadingDelay, URL-петля, useServiceQuery | модули ok/broken/slow | все слои (через `solid`) |

**Стрелки зависимостей (связи на доске):**

```
проект-потребитель ─→ react ─→ core ←─ module
        │                │        ↑
        │                └─→ storage ←─ useMedia
        │                   router (петля activeModule ↔ /:module)
        ├─→ ui (примитивы + токены проекта)
        └─→ контроллеры ─→ queries ─→ service ─┬─→ transport (api-стратегия)
                                                └─→ storage (mock-стратегия)
transport ─→ errors (ошибка → classify → шина → хендлеры)
```

`solid` — те же рёбра, что у `react` (core, storage/useMedia), плюс
router/queries-связки поверх **общих** framework-free ядер: адаптеры —
тонкие связки, ядро одно. UI-примитивы в solid-слой не портированы.

**Потребители — вне фреймворка.** Проект-потребитель (отдельный репо,
npm-зависимость shell-kit) приносит: свои токены (theme.css), домен,
вьюхи, конфиг стратегий и реестр модулей. Первый потребитель —
эталонный, доказывает механику на живом ТЗ.

## 2. Core (headless): что умеет

- **Реестр модулей** — регистрация в конструкторе и точечно; ленивая
  загрузка, preload активных; ошибка загрузки не кешируется — retry работает.
- **Видимость** — per-module предикат `enabled(state)`, пересчёт при каждом
  `setState` → список активных. Права вычисляются внутри предиката.
- **Bootstrap** — `shell.bootstrap(init)`: восстановление сессии; статусы
  `idle → bootstrapping → ready | unauthenticated | error`; активация
  модулей подавлена до готовности; «нет сессии» ≠ «упало» — auth-слот и
  перезапуск после логина. Резолв — патч состояния, видимость выводится
  обычным путём.
- **Состояние** — `getState`/`setState`/`subscribe`: контракт внешнего стора
  (useSyncExternalStore, мосты в другие сторы). Обязательное поле
  `activeModule`. Бизнес-данные, event bus и селекторы — non-goals.
- **Выбор модуля** — типизированный писатель: union id из конфига,
  рантайм-проверка по реестру. Выбор и видимость разделены: неактивный →
  рендерер покажет notFound.
- **Конфиг сервисов** — `services: { baseUrl, getToken, mockFlags }`;
  флаги моков читаются на каждом вызове — источник переключается на лету.
- **События** — изменение набора активных модулей; смена статуса.

**Осознанные non-goals ядра:** нет роутинга/URL/истории (закрыто
опциональным слоем `router` поверх контракта стора — ядро не знает
об URL); нет слотов; не решает, как рендерить; не хранит
бизнес-данные.

## 3. React-тулкит (`src/react`) — отдельный блок

**Solid 2-адаптер (`src/solid`, 2026-10-01)** зеркалит набор react:
те же провайдер/гейт/рендерер (семантика loadingDelay/pageTransition —
паритет), те же хуки + router/queries-связки (`RouterProvider`,
`usePath`, `useModuleRoute`, `useServiceQuery`). Идиоматика Solid 2
(`solid-js@2.0.0-rc.13`, optional peer): реактивные аргументы —
геттерами, возврат — аксессоры, подписки — в `onSettled`, retry —
пересозданием поддерева (keyed `<Show>`). queries — ручной порт
React-версии, не createProjection: семантический паритет важнее
идиоматики. Экспорт — `shell-kit/solid`.

Тонкий адаптер: вся логика в headless-ядре, React — только связка.
Адаптер заменяем (другой рантайм не ломает ядро).

**Компоненты:**

- `ShellProvider` — экземпляр Shell в контекст.
- `ShellGate` — ветки по статусу bootstrap: загрузка / ошибка + retry /
  неавторизован → auth-слот / готов → children.
- `ModuleRenderer` — рендер модуля по id: Suspense (ленивый чанк), Error
  Boundary с retry, notFound для неактивного/неизвестного.
- `module-lazy` — обёртка `import()` под контракт модуля (единица
  код-сплита — вариант вьюхи, не запись в реестре).

**Хуки:**

| Хук | Что даёт |
|---|---|
| `useShell()` | экземпляр Shell (setState, setActiveModule, …) |
| `useShellState()` | глобальное состояние (useSyncExternalStore) |
| `useShellStatus()` | статус инициализации |
| `useActiveModules()` | реактивный список активных модулей `{ id, loaded }` |
| `useMedia(ref)` | MediaRef → URL для `<img>`: синхронный peek из кеша (нет мерцания), асинхронный резолв, готовые URL — насквозь |

**Хуки данных** (слой `queries`): `useServiceQuery` (кеш + дедупликация,
ключ `[serviceId, метод, ...args]`), `useServiceMutation`
(mutate → инвалидация по префиксу → перечитка).

## 4. Слои данных и UI: способности

- **`service`** — стратегии mock/api, диспетчер per-call (переключение на
  лету), сервис виден только своему модулю — межмодульных связей нет.
  Реестр мок-стратегий — задел под панель управления моками.
- **`transport`** — тупая труба: конверт ответа, типизированная ошибка
  (сеть/таймаут/http/парсинг) — уходит наверх нетронутой.
- **`errors`** — классификация (вид × серьёзность × повторяемость), шина,
  готовые хендлеры: тосты/retry/auth — ошибки обрабатываются в одном месте.
- **`queries`** — порт + самописный адаптер (дедупликация параллельных,
  инвалидация по префиксу); заменяем на любую query-библиотеку реализацией
  порта.
- **`storage`** — JSON-данные в localStorage / медиа-Blob'ы в IndexedDB,
  неймспейс по проекту и сервису, версии схемы с авто-пересевом; MediaRef
  (id или готовый URL); персистентный мок write-through («создал → F5 →
  на месте»); сброс по гранулярности. Механизм рассчитан и на api-кеш.
- **`ui`** — примитивы на структурных классах (`@layer components`) +
  фабрика типизированных иконок из реестра inline-SVG. Слой не знает
  Tailwind: проект импортирует classes.css в свой theme.css и объявляет
  токены; утилиты проекта всегда сильнее структурных классов.

## 5. Обучающий контур (для людей и LLM)

- `demo/` — эталон: модуль на полном стеке (сервис api+mock → контроллер →
  чистая вьюха); импортирует ядро по имени пакета (догфудинг публичного
  API). Песочница `practice/` удалена при publish-разделении (2026-09-30).

## 6. Конвенции (предсказуемость генерации)

Контроллер = `useXxxProps`; ключ запроса `[serviceId, метод, ...args]`;
mock-флаг = id сервиса; JSDoc с примерами; в проекте — 3-слойная
архитектура (design-system → ui → transport) и 4 уровня композиции
(примитивы → блоки → виджеты → страницы).

## 8. Чего нет → куда развивать (вне текущего плана)

1. **Тестовая инфраструктура** — 0 тестов и раннеров; тест-задачи слоёв
   отложены. Для публикуемого пакета это блокер: юнит-тесты ядра
   (реестр/видимость/bootstrap) и данных — первое, что просит внешний
   потребитель.
2. **CI** — есть (`.github/workflows/ci.yml`: lint + typecheck +
   build:lib + валидация плагина + pack dry-run на push/PR);
   тестов по-прежнему нет — см. п. 1.
3. **URL / deep-link — закрыто слоем `router`** (конвенция `/:module/*`,
   режимы url/off из конфига приложения, подмена технологии адаптером
   `RouterPort`; хвосты модулей — feed/partners/messenger/resources/
   requests — на маршрутах, deep-link-поля состояния удалены).
   Осталось: query/search-параметры, hash-адаптер для хостингов без
   rewrite в index.html, типизированная таблица путей (alias корня).
4. **Пресеты модулей** — готовые проверенные модули (первый кандидат —
   авторизация), встраиваемые донастройкой (свои ручки/вьюхи/токены).
   Заявлены в ценности, в этапах плана — отсутствуют.
5. **Темы / dark mode** — токены есть, механизма переключения нет.
6. **i18n** — отсутствует целиком.
7. **a11y** — решается точечно в компонентах, системной политики нет.
8. **Телеметрия/логирование** — шина ошибок есть, отправки наружу нет.
9. **Миграции состояния приложения** — версии схемы есть у storage-скопов,
   у состояния сессии — нет.
10. **Витрина UI** — Storybook/Ladle для примитивов (люди и LLM смотрят
    готовое вместо чтения кода).
11. **Мульти-экранность** — несколько модулей одновременно на одном экране
    (закрыто идеей «зоны», не начато).
12. **Документация отстала от кода** — README не упоминает storage/practice;
    план не отражает сделанное сверх. Для Miro: сначала синхронизировать
    карты, потом строить дорожную карту.
13. **DX-мелочи** — нет script `typecheck`, нет `test`-скрипта.
