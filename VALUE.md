# shell-kit — зачем это существует

**Формула:** MVP — это конфигурация, а не проектирование. Модуль — это
заполненный контракт, а не придуманная архитектура. Дизайн — сменная
деталь. LLM — исполнитель по готовой форме, а не архитектор на месте.

Система даёт четыре измеримые выгоды. Каждая — не лозунг, а механизм
в коде, который можно показать и потрогать.

## Ц1. Быстрый MVP: сквозное — готово до старта

**Проблема.** Каждый новый проект начинается с одного и того же:
обвязка роутинга, «где хранить сессию», axios-обёртка, тосты ошибок,
retry, флаги моков «пока бэкенд не готов». Это дни работы, которая
никогда не переиспользуется — каждый пишет свою.

**Механизм.** Всё сквозное уже написано и протестировано в слоях
библиотеки:

| Задача | Слой | Что получает проект |
|---|---|---|
| Какие экраны доступны и кому | `core` + `react` | реестр, `enabled`, bootstrap, auth-ветка |
| Данные и источники | `service` + `transport` | диспетчер mock/api, конверт ошибок |
| Ошибки | `errors` | classify → шина → тосты/retry в одном месте |
| Запросы | `queries` | кеш, дедупликация, инвалидация |
| Моки без бэкенда | `service` (этап D — панель) | флаг per-service, переключение на лету |

Новый проект = подключить пакет, описать состояние и модули. Первый
экран с данными из мока — вопрос минут (эталон: модуль «Заказы» в демо,
auth-модуль в практике `services-auth`).

## Ц2. Быстро добавлять модули: одна папка + одна строка

Модуль — независимое мини-приложение по контракту `defineModule`
(вьюха или варианты + контроллер). Добавление домена:

1. папка `modules/X/`: сервис (интерфейс + стратегии), контроллер,
   чистая вьюха;
2. одна запись в реестре: `{ id, load: () => import(...), enabled }`.

Дальше всё автоматом: код-сплит (грузится только нужный чанк), видимость
(предикат от состояния, а не ручные if'ы в навигации), изоляция (сервис
не экспортируется наружу — межмодульных связей не возникает, регресс
в соседнем модуле невозможен). Скрыть модуль для роли — одна строка
в `enabled`, никакой логики в вьюхах.

## Ц3. Менять дизайн по требованию: вьюха — сменная деталь

Контракт делит модуль на **контроллер** (бизнес-часть: сервисы,
состояние, возвращает пропсы) и **вьюху** (чистая, только пропсы).
Следствия:

- редизайн экрана = подменить `component`, бизнес-часть не трогаем;
- варианты одного домена (полный/облегчённый, desktop/mobile) —
  `variants` с резолвом по пропсам, каждый вариант — свой чанк,
  грузится один;
- одна вьюха переиспользуется с другим контроллером.

Дизайнерская итерация перестаёт быть риском для логики — это замена
детали, а не вмешательство.

## Ц4. LLM понимает, как строить: контракты вместо импровизации

Главная причина, почему «попроси агента сделать фичу» сегодня даёт
случайную архитектуру: агент проектирует сам. Здесь проектировать
нечего — форма задана:

- **жёсткие контракты с типами** — `defineModule`, `defineService`,
  `enabled(state)`, `ResolveContext`: опечатка ловится компилятором,
  а не ревью;
- **конвенции имён** — `useXxxProps`, mock-флаг = id сервиса, ключ
  запроса `[serviceId, метод, ...args]`: агент предсказуем, ревьюэр
  читает код как знакомый;
- **зафиксированные границы** — реестр решений в PLAN.md и «чего ядро
  не делает» в README: пространство решений агента сужено до заполнения
  шаблона;
- **образцы для few-shot** — демо (кейсы) и практики (STEPS.md с
  пошаговым разбором эталона): это одновременно онбординг людей и
  обучающая выборка для агентов;
- **кодеген (этап E)** — самый механический слой (хуки из интерфейса
  сервиса) вообще не пишется: CLI читает интерфейс и кладёт рядом
  `hooks.gen.ts`.

Итог: промпт «сделай модуль X: сервис + мок + таблица» производит
модуль по шаблону; ревью проверяет домен, а не каркас. Каждый новый
модуль в проекте — ещё один пример, следующий дёшевле.

## Ц5. Переиспользование в любом проекте: настроить, а не переписать

Ядро headless и без домена: React — тонкий адаптер, про предметную
область библиотека не знает ничего. Пер-проектная настройка:

- `services: { baseUrl, getToken, mockFlags }` — окружение проекта;
- стратегии подменяются per-project без изменения модулей: модуль знает
  **интерфейс** сервиса, проект решает **реализацию** (свой API,
  внешний шлюз, мок);
- порты (`transport`, `errors`, `queries`) переносимы и заменяемы.

Направление роста — **модули-пресеты**: полностью готовые и оттестированные
модули (auth-модуль практики — первый кандидат), которые в новый проект
встраиваются донастройкой: подменить стратегии (свои ручки), вьюхи
(свой дизайн), токены (свой провайдер сессии). Тестируемость
наследуется: ядро и слои проверены один раз, пресет работает на моках
в любом окружении. Хуки под конкретный интерфейс генерируются кодегеном
(этап E) — бойлерплейп не пишется ни людьми, ни агентами.

## Сумма

Стоимость итерации — нового экрана, смены дизайна, смены источника
данных — падает на порядок: архитектурные решения приняты один раз
и закодированы в контрактах. Люди и LLM работают по одной форме;
проекты отличаются доменами и настройкой, а не каркасом.

## Как измеряем ценность

- **Время до первого экрана с данными** в новом проекте (цель: минуты,
  на моках — без бэкенда).
- **Стоимость нового модуля**: одна папка + одна строка реестра,
  ноль правок в существующих модулях.
- **Стоимость смены дизайна**: диф не выходит за пределы вьюхи.
- **Доля кода по шаблону** (агент/кодеген пишут, человек ревьюит)
  — растёт с каждым пресетом.
- **Работа без бэкенда**: моки переключаются на лету, демо/QA
  не ждут API.

## Когда shell-kit не нужен

- лендинг/виджет без модульности — каркас не окупится;
- проект, где URL-роутинг и SSR — жёсткие требования: ядро их не даёт
  (и не мешает принести с собой, но ценность ниже);
- прототип на один раз, который не будет жить и расти.

## Дорожная карта как усилитель ценности

Этапы PLAN.md — каждый усиливает заявленные цели:

| Этап | Что добавляет | Какую цель усиливает |
|---|---|---|
| C · SmartyClient | endpoint-map + интерцепторы: ручки как данные | Ц1, Ц5 |
| D · runtime-mock | MockPanel: тумблеры моков для QA/демо | Ц1, Ц5 |
| E · codegen | хуки из интерфейсов сервиса | Ц2, Ц4 |
| F · permissions + релиз | права в `enabled`, npm-пакет | Ц2, Ц5 |
