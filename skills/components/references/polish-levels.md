# Уровни полировки UI (L0 / L1 / L2)

Единственный источник «что из полировки применять к UI» для скиллов,
которые верстают (`prototype-to-app` — драфт) и шлифуют (`components`
— полировка готового). Проблема, которую решают уровни: полный набор
приёмов (скелетоны 1:1, фейды медиа, свапы, микро-попы) дорог и нужен
не каждому экрану — прототипу на мгновенных моках он не нужен,
прод-приложению с медленным API — жизненно. Уровень выбирается
осознанно, а не «применяем всё всегда».

## Состав

| Уровень | Имя | Когда | Что входит |
|---|---|---|---|
| **L0** | драфт-демо | быстрые демо на моках (мгновенный LS) | §48: loading = спиннер/текст; нативная семантика; без motion-полировки |
| **L1** | стандарт | база любого приложения (дефолт драфта) | всё L0 + §48 полный (empty/error/denied + отдельная ветка no-results); клавиатура/ARIA на интерактиве (полные WAI-ARIA-паттерны: стрелки, roving, aria-controls); набор состояний вида hover/focus-visible/active/disabled; reduced-motion у всех анимаций |
| **L2** | прод-полировка | готовый UI перед продом / реальный транспорт | всё L1 + скелетон 1:1 (кап обложки, line-box высоты) с шиммером; фейд-ин медиа (плейсхолдер + проявление); свап режимов (useSwapAnimation); микро-поп мутаций + оптимистичность (стейл-while-revalidate); шрифты/CSS-границы (preload критичных начертаний, render-blocking CSS) |

Детали приёмов L2: loading/медиа — `references/loading-media.md`
этого скилла; motion/мутации — инвентарь канона `SKILL.md` §B.2.

## Где хранится выбор

- **Проект вне машины prototype-to-app**: `<PROJECT_ROOT>/skills/
  PROJECT.md`, секция «UI-полировка: L<N>» (для standalone-репо приложения
  PROJECT_ROOT — корень репо; в монорепо — папка `projects/<app>/`). Нет
  файла/секции — скилл `components` на фазе locate предлагает уровень
  и фиксирует декларацию этим же ходом.
- **Сборка через prototype-to-app**: `state.json.drivers.uiPolish`
  (`l0-draft` | `l1-standard`). Спрашивается на фазе design-system —
  это уровень ДРАФТА; L2 на драфте не выбирается — это поздний
  полировочный проход (см. ниже).

## Поток «сначала драфт, потом красота»

1. **Драфт**: prototype-to-app → вопрос фазы design-system →
   `drivers.uiPolish` (обычно L1; L0 — чистое демо). Вёрстка модулей
   выполняется на этом уровне (уровень передаётся субагентам модулей).
2. **Готовое приложение**: hardening предлагает полировочный проход —
   по экранам скиллом `components`, уровень L2, повестка из дыр
   аудита (`references/component-audit.md`) по разнице текущий → L2.
3. **Фиксация**: итог — секция «UI-полировка» + строки-эталоны в
   `skills/PROJECT.md` проекта; дальнейшие прогоны `components` читают
   декларацию, а не спрашивают заново.

## Правила

- Уровень — рамка **повестки**, не запрет: дыра ниже уровня всё равно
  попадает в открытые вопросы аудита; приёмы выше уровня —
  предложением («поднять уровень?»), не молча.
- Уровень проекта может уточняться пер-экраном (демо-экран L0 внутри
  L2-проекта) — осознанное решение фиксируется в PROJECT.md.
- Гигиена (нативные элементы, контраст, безопасные ссылки) не зависит
  от уровня — это не полировка, а ось 9 аудита.
- Смена уровня — решение пользователя; скилл может предложить,
  применяет — только после подтверждения.
- Прототип — драфт, не детальный референс: он нужен, чтобы начать
  верстать проект. Полировка не «догоняет прототип» — она приводит
  экраны максимально к единому виду проекта; сверка с прототипом
  1:1 не является целью уровня.
