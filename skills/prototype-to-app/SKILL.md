# /prototype-to-app

Оркестратор превращения **кликабельного HTML-прототипа** в целостное
модульное приложение поверх платформы-оболочки (shell-kit-подобной:
`defineModule` / `defineService` / AppState). В отличие от
`prototype-to-react` (источник дизайна → дизайн-система одного экрана),
этот скилл ведёт **всю ширину приложения** как **стейт-машину со
сменными фазами-промтами и журналом договорённостей**.

Скилл живёт в репозитории платформы: `skills/prototype-to-app/`
(исходник истины, версионируется вместе с контрактами ядра). Запуск —
без глобальной регистрации, из проекта-потребителя (см. §I). Дока-страница
для человека — `docs/index.html` рядом с этим файлом.

## A. Модель: стейт-машина, а не сценарий

Состояние процесса живёт в целевом проекте и переживает сессии; файлы
фаз в этом скилле — сменные промты. Граф:

```
intake → shell-decisions → skeleton → design-system
   → ( modules.map → refactor ) × батчи 1..N
   → hardening → done
```

- **modules** — очередь, а не фаза: N модулей, батчами по готовности.
- **design-system** и **refactor** — реентерабельные (перевход по циклу).
- Внутрь каждого модуля вложена под-машина
  `plan → types → [service ‖ views] → glue → review` (см.
  `phases/modules-map.md`).

## B. Старт сессии (обязательный алгоритм)

1. Найди `<PROJECT_ROOT>/.app-build/state.json` (`PROJECT_ROOT` = cwd,
   если в ней `package.json` и `src/`; иначе поднимайся вверх).
2. **Нет файла** → первый запуск: выполни `references/phases/intake.md`.
3. **Есть файл** → сверь `stateVersion` с `references/state-contract.md`
   (при расхождении — миграции, §G), затем спроси режим сессии через
   `AskUserQuestion`:
   - **auto** — идти по графу, останавливаясь только на содержательных
     гейтах;
   - **step** — один шаг (фаза/подфаза), остановка и отчёт;
   - **pick** — выбрать фазу из реестра §D, в т.ч. вернуться к прошлой.
4. Режим по умолчанию для возобновлённой сессии — `auto`; выбранный
   режим запиши в `state.json.sessionMode`.

## C. Хранилища процесса

| Хранилище | Путь | Роль |
|---|---|---|
| Машина | `.app-build/state.json` | фаза, очередь модулей, драйверы, stale |
| Договорённости | `.app-build/decisions.md` | журнал D-xxx: вопрос / решение / последствия |
| Артефакты | `.app-build/artifacts/` | планы модулей, типы, отчёты refactor/DS |

Контракт — `references/state-contract.md`. Правило: любое решение,
меняющее потребителей, фиксируется D-записью **до** продолжения работы.
Субагенты не пишут в state.json — стейт двигает только оркестратор.

## D. Реестр фаз

| Фаза | Файл (`references/…`) | Полнота | Реентерабельность |
|---|---|---|---|
| intake | `phases/intake.md` | каркас | повторный вход = осознанный ресет |
| shell-decisions | `phases/shell-decisions.md` | каркас | да |
| skeleton | `phases/skeleton.md` | каркас | да |
| design-system | `phases/design-system.md` | **полная** | да (пополняется из refactor) |
| modules.map | `phases/modules-map.md` | каркас | да (батчи) |
| module-plan (внутр.) | `phases/module-plan.md` | каркас | да |
| refactor | `phases/refactor.md` | **полная** | да (после каждого батча) |
| hardening | `phases/hardening.md` | каркас | да |

«Каркас» = контракт и наводящие вопросы заполнены, детальные
инструкции дописываются по мере обкатки. Помечай фактическую полноту
честно и не выдавай каркас за полную фазу.

## E. Контракт фазы

Каждая фаза обязана соответствовать единому контракту
(`references/phase-contract.md`): назначение / вход / наводящие вопросы
с дефолтами / действия / выход (артефакт + диф стейта) / гейт /
изоляция записи. Оркестратор читает файл фазы и следует ему буквально.

## F. Параллелизм (map-reduce)

**Межмодульный (map)**: после skeleton + design-system модули собираются
параллельно — по субагенту на модуль батча:

- агент пишет **только в папку своего модуля** и его точку регистрации;
- `shared/`, конфиги shell, чужие модули — **закрыты**; необходимые
  изменения там оформляются патч-предложением, применяет оркестратор
  на reduce;
- preset-модуль (1 экран, CRUD) — 1 агент; крупный домен — 2 агента
  (service ‖ views после types); сквозные сетки (мессенджер и т.п.) —
  всегда отдельным батчем.

**Внутримодульный (types-first)**: план модуля первым коммитом
выпускает типы (домен + интерфейс сервиса + union vm) → `service` и
`views` пишутся параллельно → `controller` — клей поверх готовых типов.

**reduce/refactor**: после батча — применение патчей и канонизация
дублей (`phases/refactor.md`), затем следующий батч.

## G. Правила машины

- **Гейты** двух сортов: тривиальный («продолжаем?») и содержательный
  (вопросы с вариантами и последствиями). Режим `auto` останавливается
  только на содержательных.
- **Переоткрытие решения**: D-запись получает статус `пересматривается`,
  её consumers попадают в `state.stale[]`; затронутые фазы обязаны
  выполнить свои invalidate-правила до продолжения.
- **Миграции**: `stateVersion` в state.json; изменение схемы в
  state-contract.md обязано сопровождаться миграцией n→n+1.
- **Идемпотентность**: повторный вход в фазу не ломает сгенерированное —
  перед записью проверяй существующее (filesystem probing, `Glob`).
- **Честность**: если задача выходит за рамки каркасной фазы —
  остановись и спроси, дописать ли фазу (это и есть развитие скилла).

## H. Заменяемость блоков

- **L1 — файл**: фаза целиком сменный промт (переписать `phases/x.md`).
- **L2 — драйвер**: вариант по ключу из state.json (`drivers.styling` →
  `drivers/styling/tailwind.md` | `drivers/styling/css-modules.md`;
  `drivers.adaptivity` → `drivers/adaptivity/prototype-canon.md`).
  Новый вариант = новый файл в `drivers/<семейство>/` + запись в
  state-contract.md.
- **L3 — пример**: канонический пример внутри текста фазы; меняется
  локально без перестройки фазы.

Развитие скилла — чаще всего L1/L3-правка одного файла фазы; тестирование
альтернативных подходов — L2-драйвер или копия фазы с суффиксом.

## I. Запуск из проекта-потребителя

Скилл не регистрируется глобально и не нуждается в симлинках — это
промт-файлы в репозитории платформы:

1. **Точка входа** — память проекта-потребителя (например, `MEMORY.md`
   в корне проекта): раздел «Скиллы платформы» с реестром имён и
   правилом резолва пути. Агент читает её в каждой сессии — этого
   достаточно для обнаружения.
2. **Резолв пути** (первый сработавший):
   - проект в монорепо shell-kit → подняться до корня репозитория →
     `<root>/skills/<name>/SKILL.md`;
   - скиллы установлены как плагин → соседние скилы — сиблинги
     папки этого скилла: `../<name>/SKILL.md`;
   - фолбэк → `node_modules/shell-kit/skills/<name>/SKILL.md`.
3. **Команды пользователя**: «запусти prototype-to-app», «продолжи
   конвейер», «пройди фазу X» → агент читает SKILL.md целиком и
   действует как оркестратор (старт сессии — §B).
4. Всё, что переживает сессии, лежит в самом проекте (`.app-build/`),
   поэтому продолжение не зависит от способа запуска.
