# Фаза: refactor

Статус: **полная**. Реентерабельность: да — фаза задумана как цикл
после каждого батча modules.map.

## Назначение

Канонизация: найти компоненты, написанные разными модулями (или одним
модулем) похоже, и поднять общее в shared — канонично, а не копипастой.
Второй потребитель, которого не было видно в прототипе, проявляется
только здесь — поэтому refactor обязательный участник цикла, а не
гигиена напоследок.

## Вход

- Завершён батч modules.map (все модули батча `status: done|review`).
- `artifacts/design-system.md` (текущий реестр фонда).

## Наводящие вопросы (дефолты)

- **Q1 Порог включения кандидата в отчёт?** Дефолт: два экземпляра в
  разных файлах И схожесть структуры (не только текста). Обоснование:
  дубли текста/конфига — часто просто совпадение.
- **Q2 Что делать с расхождениями при подъёме?** Дефолт: канон —
  классы прототипа (как в design-system); расхождения → пропсы.
  Если экземпляры расходятся сильнее пропсов — не объединять.

## Действия

### 1. Детект похожих (четыре сигнала)

1. **Кластеры утилитарных классов** — почти одинаковые наборы классов
   в разных компонентах (нормализация порядка, сравнение множеств).
2. **Семантическая структура** — одинаковые деревья тегов/ролей при
   разных классах (проверять, если стилизация уехала в драйвер-вариант).
3. **Пропс-сигнатуры** — пересекающиеся наборы пропсов у компонентов
   разных модулей (`{id, title, badge, action}` — запах общего блока).
4. **Дубли текстов/конфигов** — повторяющиеся наборы строк (лейблы
   состояний, заглушки §48) — кандидаты в конфиг shared.

Сигналы независимы: совпадение любого — повод посмотреть руками;
подъём — при совпадении структуры (сигналы 1–3) или явном повторе
конфига (сигнал 4).

### 2. Отчёт кандидатов

`artifacts/refactor/report-<n>.md` (n = `state.refactorCycle`), для
каждого кандидата:

```markdown
## R-3 ItemCard ↔ PartnerRow
- Где: modules/requests/RequestCard.tsx; modules/partners/PartnerRow.tsx
- Сигналы: классы (12 общих), пропсы ({id,badge,summary,action})
- Дифф канонизации: <unified diff>
- Куда: shared/ItemCard (реестр DS, раздел «v2»)
- Риск: партнёрская строка теряет X — решается пропсом extraBadge
```

Кандидаты **только предлагаются** — код не меняется до гейта.

### 3. Канонизация (после гейта)

- канон: разметка прототипа; расхождения → пропсы; сильные расхождения
  → два блока;
- поднимаются только утверждённые кандидаты; отклонённые остаются в
  отчёте с пометкой (чтобы не предлагать повторно без новых причин);
- каждое поднятие = D-запись (consumers: оба модуля) + строка в
  реестре DS;
- затронутые модули переводятся в `status: review` с invalidate
  конкретных файлов (не всего модуля).

### 4. Решение цикла

- есть утверждённые кандидаты → применить → `refactorCycle++` →
  следующий батч (модули следующего батча сразу используют пополненный
  фонд);
- кандидатов нет или все отклонены → цикл завершён; очередь пуста →
  `hardening`, иначе → следующий батч.

## Выход

- Артефакт: `artifacts/refactor/report-<n>.md`; код — поднятые блоки,
  обновлённые импорты модулей.
- state.json: `refactorCycle` (+1 при применении), `modules.queue`
  (следующий батч / переход к hardening), `stale` — при изменениях,
  задевающих чужие договорённости.

## Гейт (содержательный)

По каждому кандидату: поднять как общий блок / оставить как есть /
объединить сильнее (пометить причину). Показывать диффы, а не описания.

## Изоляция записи

- Разрешено: папка shared-блоков, `artifacts/refactor/*`, импорты в
  затронутых модулях (точечно, по списку гейта), реестр DS.
- Запрещено: логика модулей (только замена компонента на shared-аналог),
  конфиги shell, state.json вне предписанного дифа.
