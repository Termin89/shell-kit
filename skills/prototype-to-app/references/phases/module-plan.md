# Под-фаза: module-plan

Статус: каркас. Реентерабельность: да (перепланирование = новый
план + D-запись). Это под-фаза modules.map: выполняется для одного
модуля до включения его в батч.

## Назначение

План-договор модуля: граница, сущности, режимы экранов, карта
компонентов с уровнями. План дешевле кода — все дорогие решения
принимаются здесь, а субагенты лишь исполняют. Продукт плана — также
`types.md`, разблокирующий параллельность внутри модуля.

## Вход

- Модуль в очереди; экран(ы) модуля из прототипа; реестр DS;
  классификатор уровней (`classifiers/component-levels.md`).

## Наводящие вопросы (дефолты)

- **Q1 Граница модуля?** Что НЕ входит (кандидаты в другие модули /
  shared / вообще мимо продукта).
- **Q2 Сущности и владение?** Список сущностей домена, их поля и
  статусы; чьи сущности (Q8 shell-decisions).
- **Q3 Режимы экранов?** Список режимов/перспектив одного модуля
  (например: список / карточка / создание; своя vs «зеркальная»
  роль-перспектива). Каждый режим и каждое состояние данных (§48:
  loading/empty/error/denied/notFound) попадает в union vm —
  типизированный union, не булевы флаги. Контракт vm —
  `../vm-contract.md` (состав, применимость по рангам; проект не
  на vm — уточнить у владельца, зафиксировать D-записью).
- **Q4 Навигация?** Какие режимы — URL-сегменты (deep link, F5),
  какие — локальный стейт (шаги визарда, табы).
- **Q5 Сервис?** Интерфейс доменного сервиса (мок-стратегия сейчас,
  api-стратегия потом), персистентность мока, мутации.
- **Q6 Карта компонентов?** Каждому компоненту — уровень по
  классификатору + колонка «второй потребитель?» (кандидат в shared)
  + контракт по рангу: vm-срез или узкие пропсы (`../vm-contract.md`).

## Действия

1. Прочитать экраны модуля в прототипе.
2. Ответить на Q1–Q6 (дефолты обосновывать прототипом).
3. Записать `artifacts/modules/<id>/plan.md` (секции — по вопросам).
4. Выпустить `artifacts/modules/<id>/types.md`: доменные типы +
   интерфейс сервиса + union vm. Это первый коммит кода модуля —
   types-first.

`<!-- L3: пример каркаса types.md -->`
```ts
/* Домен */   export interface RequestData { id: string; status: RequestStatus; … }
/* Сервис */  export interface XxxService { list(): Promise<RequestData[]>; … }
/* vm-union */ export type RequestsVm =
                | { mode: "list"; status: "loading" }
                | { mode: "list"; status: "content"; requests: RequestData[]; … }
                | { mode: "detail"; status: "notFound" } | …;
```
`<!-- /L3 -->`

## Выход

- Артефакты: `plan.md` + `types.md` модуля.
- state.json: `modules.items[<id>].status → "planned"`.

## Гейт (содержательный)

План перед пользователем: подтвердить / изменить границу / пометить
сомнительное. Только после подтверждения модуль попадает в батч.

## Изоляция записи

- Разрешено: `.app-build/artifacts/modules/<id>/**`.
- Запрещено: код модуля (кроме первого коммита types по утверждённому
  плану), shared/, state.json вне дифа фазы.
