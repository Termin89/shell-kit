# Фаза: design-system

Статус: **полная**. Реентерабельность: да (повторный вход только
дополняет реестр, ничего не удаляет).

## Назначение

Собрать дизайн-систему уровня **всего прототипа**: токены, примитивы и
`shared v1` — блоки, чей второй потребитель виден в самом прототипе
статически. Это фонд, из которого параллельные модули будут собираться
без договорённостей между собой.

## Вход

- `state.phase == "skeleton"` (артефакты: `modules-registry.md`).
- Прототип доступен по `state.source.ref`.
- Если чего-то нет — вернуться на предыдущую фазу, не импровизировать.

  токены дешёвые, межмодульные договорённости дорогие. Всё уникальное

- **Q3 Где живёт shared?** Дефолт: платформенная папка shared-блоков

- **Q4 Уровень полировки драфта?** `<!-- L2: drivers.uiPolish -->`

  на интерактиве, hover/focus-visible, reduced-motion; база любого
  приложения) / `l0-draft` (чистое демо на мгновенных моках: §48

Ответы фиксируются D-записями (включая дефолты — см. state-contract.md).

## Действия

### 1. Проход «токены и примитивы» — делегирование

Токены и примитивы не извлекаются заново — делегируй скиллу
`prototype-to-react` по фазам:

```
prototype-to-react <state.source.ref> --phase design      # токены
prototype-to-react <state.source.ref> --phase primitives  # примитивы
```

Обоснование: источник дизайна один и тот же, контракт отчёта и
стайлинг-конвенции у prototype-to-react уже выверены. Дублирование
логики здесь — источник рассинхрона.

Правило уровня: **примитив не знает домена**. Компонент, в типах
которого появились сущности предметики (заявка, тариф, партнёр), —
не примитив; верни его в кандидаты блоков (проход 2).

### 2. Проход «блоки-повторы» — статический поиск shared v1

Второй потребитель блока виден в самом HTML-прототипе: одинаковые
структуры, повторяющиеся на разных экранах. Ищи:

- **кластеры классов**: одинаковые/почти одинаковые наборы классов
  (нормализовать порядок, сравнить как множество);
- **семантические паттерны**: повторяющиеся деревья тегов/ролей
  (шапки карточек, строки «метка–значение», пустые состояния);
- **повторы с вариацией**: структура та же, тексты/иконки разные —
  это один блок с пропсами, а не два.

Для каждого кандидата — канонизация: **каноном считается разметка
прототипа**, расхождения между экземплярами уходят в пропсы. Если
экземпляры расходятся сильнее чем на пропсы — это два блока, не один
(не насильственно объединяй).

`<!-- L3: пример канонизации -->`
```text
экземпляр A (экран «Мои запросы»):  <div class="card …"> [номер][бейдж][сводка][кнопка]
экземпляр B (экран «Входящие»):     <div class="card …"> [номер][бейдж][текст][кнопка]
→ блок shared/ItemCard: props { id, badgeTone, badgeLabel, summary, action }
```
`<!-- /L3 -->`

### 2a. Канон геометрии (уроки прогонов)

Вёрстка переносится 1:1, не «улучшается» на глаз:

- **Строка списка — плоская строка.** Если в прототипе строка без
  рамки (`border-bottom`-разделитель, `:last-child` без границы,
  hover — цвет-подложка) — примитив/блок воспроизводит геометрию
  точно: без рамки/радиуса/собственного фона и без gap-обёрток.
  «Карточка в карточке» — типовой дрейф, запрещена, если её нет
  в источнике. Строки живут в карточке-секции **во всю ширину**:
  секция без набивки, строки — прямые дети.
- **Тип сложных компонентов сверяется с прототипом.** Степпер бывает
  «прогресс-линией» (сегменты + линия с точками + подписи по центру)
  или «чипами» — переносится разновидность источника.
- **Медиа-запросы переносятся все.** Каждый `@media` прототипа
  отражается утилитами-брейкпоинтами или медиа-блоком в theme.css
  (включая `flex-wrap`/`min-width` шагов визардов). Ширина медиа →
  ближайший брейкпоинт фреймворка, допуск — D-записью.
- **Мобильная адаптация канона** `<!-- L2: drivers.adaptivity -->`:
  если прототип десктоп-only, раскладка ниже брейкпоинтов — по
  драйверу `drivers.adaptivity` (grid-item'ы `min-width:0`,
  компонентные классы только в `@layer components`, шапки экранов
  столбцом <md, навигация бургером <lg). Десктоп — по канону
  прототипа, мобильная раскладка — производная, фиксируется
  D-записью.
- **Валидация — числами.** computed-style пробы (`getComputedStyle`:
  padding, border-*, grid-template-columns, line-height) против
  канона прототипа; скриншоты — только дополнение (см. hardening).

### 3. Реестр DS

Запиши `artifacts/design-system.md`: токены (ссылкой на отчёт
prototype-to-react), примитивы, блоки shared v1 с каноническими
подписями пропсов. Это вход и для модулей, для циклов refactor и для
каталога (шаг 4).

### 4. Каталог (опционально)

`<!-- L2: drivers.catalog -->` По желанию пользователя — делегирование
в скилл `storybook` (резолв — §I): каталог фонда v1
(примитивы + блоки shared). Драйвер — `state.json.drivers.catalog`
(дефолт `storybook`). Не блокирует батчи: каталог можно собрать позже,
на любой фазе, и в любом проекте — скилл работает и без машины.

## Выход

- Артефакт: `artifacts/design-system.md`; код — токены/`theme`,
  примитивы, `shared v1`.
- state.json: `phase → "modules.map"`; `drivers.uiPolish` (Q4);
  `drivers.catalog` — если выбран на шаге 4; `decisions` +D (Q1–Q4).

## Гейт (содержательный)

Список блоков shared v1 + вопрос: «этого фонда достаточно для первого
батча модулей?» Варианты: достаточно / добавить блок X / убрать блок Y.
Явно проговорить: полнота не требуется — refactor дособерёт после
батча; здесь фиксируется только то, у чего второй потребитель уже виден.
