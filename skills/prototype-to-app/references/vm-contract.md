# Контракт вьюхи: vm (MVVM) и семья альтернатив

Единственный источник «как вьюха получает данные и поведение».
Канон платформы — **vm (view model, MVVM)**; здесь же — правило
расширения: другие контракты (MVC-стиль, свой) подключаются
решением владельца, а не молча (раздел «Семья контрактов»).

## Концепция

Вьюха — тупая функция отрисовки; vm — единственный аргумент:
всё готовое к показу (данные + поведение), собранное контроллером.

```
service (домен)          controller               view
сырые записи,  ──►  вычислить/отфильтровать  ──►  FeedList(vm: FeedListVm)
статусы, LS          + права + тексты +          «что получила — то
                      колбэки ⇒ FeedVm            нарисовала»
```

Состав vm — три вида полей:

- **производные данные** — уже вычисленные (`cards`, `noResults`),
  вью ничего не считает;
- **поведение** — готовые обработчики (`onOpenCard`,
  `onQueryChange`), вью дергает, логики не содержит;
- **выбор состояния** — решение уже принято (`status: "loading" |
  "error" | …`, `mode`), вью только мапит ключ на заглушку/зону.

Сборщик ровно один — контроллер. Тип vm (`FeedListVm` в
`controller.ts`) — документация экрана: полный список того, что
нужно вью. Что это покупает:

- тестируемость — вью рендерится от литерального объекта, без
  моков сервисов/роутера (на этом стоит storybook-скилл);
- ноль логики в JSX — вся подготовка в одном месте;
- границы слоёв — pages не импортируют сервисы, сервисы не знают
  React; vm — единственный мост.

Стиль кода: компонент объявлен как `function FeedList(vm:
FeedListVm)`, вызов `<FeedList {...vm} />` — props-объект и есть
vm, поля становятся пропсами.

## Применимость по рангам

Критерий для серой зоны (экранные блоки): **решает ли блок, что
рендерить по состоянию экрана** (статус §48, режим, права,
no-results). Решает — получает vm (срез или под-объект);
отрисовывает уже выбранную единицу данных — узкие пропсы.

| Ранг | Пример (u-kon feed) | Контракт |
|---|---|---|
| Экран-страница | `FeedPage` | vm-union целиком |
| Зона режима | `FeedList` / `FeedPost` | срез vm (`FeedListVm`) |
| Блок-композитор зоны | `FeedPageActions`, `FeedComments` | vm зоны / под-объект (`vm.comments`) |
| Блок-единица данных | `FeedCard` | узкие пропсы (`card`, `onOpen`) |
| Элемент | `FeedCardStats` | узкие пропсы |
| Shared-блок / виджет / примитив | `ListToolbar`, `Button` | узкие пропсы, никогда vm |

```
Блок решает, ЧТО рендерить по состоянию экрана?
├─ ДА  → vm: срез или под-объект
└─ НЕТ → узкие пропсы (единица данных)
```

Практические сигналы: блоку нужно 4–5+ полей из одного vm, среди
них статусы/права/колбэки — это контракт зоны, тащите vm (срез).
Блоку хватит 1–2 полей (данные + один колбэк) — узкие пропсы,
даже если блок крупный. Миграция в любую сторону — обычная
правка с обновлением потребителей.

## Семья контрактов (расширяемость)

vm — дефолт платформы, но не догма. Возможные альтернативы:

- **MVC-стиль** — вьюха принимает не подготовленный vm, а модель +
  тонкий адаптер (когда данные приходят готовыми с бэкенда и
  подготовка тривиальна);
- **props-driven / слоты** — родитель собирает контент детьми,
  контракта данных нет (каркасные shell-компоненты);
- **свой контракт** — описывается здесь новой секцией по той же
  схеме: концепция → состав → применимость → пример.

Правила:

- Выбор контракта — **решение владельца проекта**, не скилла.
  Скилл уточняет: на module-plan (типы vm-union) и при ревью
  вьюх (components) — «этот проект на vm или на другом
  контракте?», не молча подменяет.
- Отступление от vm фиксируется D-записью (prototype-to-app)
  или секцией в `skills/PROJECT.md` проекта (components) —
  с мотивировкой и границами применения.
- Внутри одного модуля — один контракт; смешение (зона на vm,
  соседняя на MVC-пропсах) — стоп-сигнал на ревью.

## Чекпойнты (для фаз и ревью)

- Вьюха не импортирует сервисы и не зовёт запросы — только vm.
- В vm нет сырых доменных записей там, где вью нужна производная
  (форматирование/фильтрация — работа контроллера).
- Смена контракта блока (пропсы ↔ vm) не меняет его разметку.
- Обработчики в vm стабильны на ре-рендере, где это важно
  (memo-потребители), либо потребитель не memo — осознанно.
