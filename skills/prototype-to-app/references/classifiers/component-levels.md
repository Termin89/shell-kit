# Классификатор: уровни компонентов

Единое решающее дерево «куда кладём компонент» для планов модулей и
фазы refactor. Применимо к любой платформе с четырьмя уровнями:
примитивы / блоки (shared) / виджеты / страницы.

## Дерево решения

```
Компонент знает домен (сущности предметики, статусы, сервис)?
├─ ДА → СТРАНИЦА  src/ui/pages/<module>/…
│        ├── один экран          → файлы в корне папки модуля,
│             блоки — components/
│        └── 2+ режимов/экранов  → views/<экран>/ (папка экрана =
│             файл слайса контроллера = ключ vm), кросс-экранные
│             блоки — shared/; рамка-диспетч наверху
├─ НЕТ, но знает каркас приложения (навигация, роли, layout, auth)?
│   └─ ДА → ВИДЖЕТ  (каркасные: shell-сайдбар, топбар, guards)
├─ НЕТ, но есть второй потребитель (повтор в прототипе или после
│   map-батча)?
│   └─ ДА → БЛОК shared/  (канонизация, см. ниже)
└─ НЕТ, только форма/презентация (кнопка, бейдж, дропзона)
    → ПРИМИТИВ ui/  (токены и только токены в пропах)
```

Порядок вопросов важен: домен доминирует. Строка таблицы с бейджами
статусов — страница, а не блок, если статусы — статусы домена.

## Признаки уровня (короткая шпаргалка)

| Уровень | Знает | Не знает | Маркер в коде |
|---|---|---|---|
| Примитив | токены, свою форму | домен, каркас, других | пропсы — строки/токены, детей |
| Блок shared | форму + слот под данные | откуда данные, кто зовёт | принимает данные пропсами, сам ничего не грузит |
| Виджет | каркас приложения | предметику экранов | обращается к AppState/навигации |
| Страница | домен модуля целиком | чужие модули | vm из контроллера, сервисы модуля |

## Ранги внутри страницы (масштаб ≠ слой)

Слой отвечает «где файл и кто может импортировать»; ранг — «какую
зону ответственности занимает». Это два измерения: блок shared по
слою может быть рангом «элемент» (Icon), а «экранный блок» по рангу
живёт в слое страницы, потому что знает домен.

| Ранг | Владеет | Маркер в коде |
|---|---|---|
| Экран-страница | маршрутом/слотом, контроллером (vm), layout-рамкой | default export `pages/<module>/`, зовёт `use<Module>Controller` |
| Экранный блок | зоной экрана (карточка/панель/форма/список): своя композиция + `data-name`, данные — через vm/колбэки, не через сервисы | функция-компонент в папке модуля (для 2+ режимов — `views/<экран>/`) |
| Элемент | одной единицей представления (поле, строка ошибки, бейдж) | десятки строк рядом с блоком, экранной зоны нет |

Какой ранг какой контракт получает (vm vs узкие пропсы) —
`../vm-contract.md`: критерий «решает ли блок, что рендерить по
состоянию экрана» + матрица по рангам.

Порог выделения inline-разметки в блок: вторая точка
переиспользования, собственные состояния/эффекты, либо файл блока
распух (3+ условных ветвей контента). Ранг задаёт план проверки
правки: элемент → все блоки-потребители, блок → все режимы экрана,
страница → весь модуль.

Пример (auth, 2026-09-24): `AuthScreen` — экран-страница, после
декомпозиции владеет только рамкой (aside + слот карточек со свапом
по режиму) → блоки в `components/`, один блок — один файл:
`AuthCard` / `LoginForm` / `RegisterForm` / `PendingCard` /
`RecoveryCard` / `RecoverySentCard` (+ `RoleHint` — демо-инструмент,
отдельным файлом там же) → элементы `Field` / `ErrorNote` (общие трём
формам, свой файл). Формы вынесены из inline-JSX решением владельца
до порога повтора — расхождение зафиксировано в auth-memory.

**Повтор внутри экрана ≠ shared.** «Второй потребитель» из дерева
слоёв — это потребитель в другом модуле, а не второй вызов на том
же экране. Формы login/register/recovery одного auth используют
одно Field (8 вызовов) и один скелет «form+submit+error» (3 копии)
— это кандидаты в локальные блоки папки модуля, не в `ui/shared`;
подъём в shared — вместе с межмодульным потребителем. Обратное
тоже правило: повтор вызова примитива (`Button variant="ghost"`
в трёх карточках) — не повод для обёртки; извлекается повтор
разметки, а не повтор вызова.

**Один блок — один файл.** Владение множеством компонентов —
самостоятельный порог декомпозиции, независимо от повтора: блок
ранга «экранный блок» живёт в своём файле (`components/` папки
модуля), экран-страница после декомпозиции владеет только рамкой
и слотами. Мотивировка — когнитивная нагрузка и для человека, и
для агента: точечное чтение (открыть RegisterForm, а не листать
экран целиком), точечные дифы при правках, граф импортов как
навигационный индекс. Элемент может жить рядом с блоком-создателем;
свой файл — со второго потребителя.

**Один экран — один tsx в корне.** В корне папки модуля лежит
только главный компонент страницы (default export) и не-компонентные
файлы (controller/config/service/module/routes); остальные
компоненты — по зонам владения: одноэкранный модуль — `components/`,
мультирежимный — `views/<экран>/` (папка экрана = файл слайса
контроллера = ключ vm-union: структура символически декларирует
подстраницы, новый экран = новая папка + слайс + ключ) и
кросс-экранные блоки — `shared/`. Корень = оглавление модуля:
состав экранов и зон виден без открытия файлов. Эталоны u-kon:
feed (`views/list|post|my|editor|admin` + `shared/`,
2026-09-27), auth (`components/`); зоны корневыми папками без
контейнера (messenger, requests) — кандидаты на перенос на
`views/` + `shared/`.

## Правила применения

- **Кандидаты записываются заранее**: в плане модуля (`module-plan`)
  у каждого компонента указан уровень и колонка «второй потребитель?».
  Refactor проверяет эти прогнозы, а не ищет с нуля.
- **Подъём = канонизация, не копипаста**: общий блок собирается по
  канону прототипа, расхождения → пропсы. Перенос «как есть» с общим
  предком ради переиспользования — запрещённый путь.
- **Понижение тоже бывает**: страница без доменных знаний вырождается
  в блок; примитив, обросший предметикой, — в страницу. Понижение
  фиксируется D-записью (consumers: план модуля).
- **Пограничный случай** (каркас + чуть домена, например бейдж статуса
  в топбаре): доменную часть передавать данными/слотом; компонент
  остаётся виджетом/блоком.
- **Прямые связи между модулями запрещены**: если двум модулям нужен
  один компонент — это shared-кандидат, а не импорт из чужой папки.
