prototype-to-app / skills/prototype-to-app

Скилл-оркестратор shell-core: превращает кликабельный HTML-прототип в целостное модульное приложение поверх платформы (defineModule / defineService / AppState). Ведёт процесс как стейт-машину со сменными фазами-промтами: состояние переживает сессии, договорённости фиксируются журналом, модули собираются параллельно.

shell-core · конвейер «HTML → проект» состояние: .app-build/ в целевом проекте делегирует prototype-to-react для токенов/примитивов запуск: из проекта-потребителя, без регистрации

01Граф машины

Файлы фаз — сменные промты; машина живёт в целевом проекте. modules — очередь (батчи), а не фаза; design-system и refactor реентерабельны и питают друг друга циклом.

02Хранилища процесса

Скилл не держит состояние в памяти: всё, что переживает сессии, лежит в целевом проекте. Субагенты стейт не трогают — его двигает только оркестратор.

.app-build/state.json

Машина: текущая фаза, режим сессии, очередь модулей и под-фазы, драйверы (например styling: tailwind | css-modules, adaptivity: prototype-canon), счётчик решений, список stale. Схема версионируется, миграции описаны в контракте.

.app-build/decisions.md

Журнал договорённостей D-xxx: вопрос / решение / последствия / consumers. Дефолтные ответы тоже фиксируются — иначе регенерация разъедется с прошлым прогоном. Переоткрытие решения отправляет его consumers в stale.

.app-build/artifacts/

Плоды фаз: реестр модулей, реестр дизайн-системы, планы модулей с типами (types.md разблокирует параллельность), отчёты refactor-циклов.

03Сессия и реестр фаз

На старте сессии оркестратор читает state.json и спрашивает режим: auto — до ближайшего содержательного гейта, step — один шаг с отчётом, pick — выбрать фазу из реестра (в том числе вернуться). Гейты двух сортов: тривиальный («продолжаем?») и содержательный (вопросы с последствиями) — auto останавливается только на содержательных.

04Параллелизм

map-reduce между модулями

По субагенту на модуль батча. Агент пишет только в папку своего модуля; shared/, конфиги shell и чужие модули закрыты — нужные изменения возвращаются патч-предложением, применяет оркестратор на reduce. Preset-модуль — 1 агент; крупный домен — 2; сквозные сетки — отдельным батчем.

types-first внутри модуля

План первым коммитом выпускает типы — домен, интерфейс сервиса и типизированный union vm (режимы × состояния §48, не булевы флаги). Дальше сервис и вьюхи пишутся параллельно, контроллер — клей поверх готовых типов.

plan→ types (первый коммит)→ service∥ views→ glue (контроллер)→ review

05Классификатор уровней компонентов

Единое решающее дерево «куда кладём компонент» для планов модулей и refactor. Порядок вопросов важен: домен доминирует. Подъём в shared — канонизация по разметке прототипа, расхождения уходят в пропсы; копипаста общего предка запрещена. 

Компонент знает домен (сущности предметики, статусы, сервис)?
├─ ДА → СТРАНИЦА   src/ui/pages/<module>/…  · 2+ режимов → подпапки (wizard/, detail/)
├─ НЕТ, знает каркас (навигация, роли, layout)? → ВИДЖЕТ
├─ НЕТ, есть второй потребитель (повтор)? → БЛОК shared  канонизация, не копипаста
└─ НЕТ, только форма/презентация → ПРИМИТИВ ui  токены и только токены в пропах

06Заменяемость блоков

Скилл задуман как набор сменных промтов — развивать и тестировать блоки можно по отдельности.

L1 · файл

Фаза целиком — сменный промт: переписать phases/x.md по контракту из phase-contract.md. Развитие скилла — чаще всего L1-правка.

L2 · драйвер

Вариант по ключу из state.json: drivers.styling → drivers/styling/tailwind.md | css-modules.md, drivers.adaptivity → drivers/adaptivity/prototype-canon.md (мобильная адаптация десктопного прототипа). Смена одного ключа меняет конвенции всех фаз, не переписывая их.

L3 · пример

Канонический пример внутри текста фазы (<!-- L3 -->) — подменяется под проект локально, без перестройки фазы.

Исходник истины — файлы скилла в репозитории платформы (skills/prototype-to-app). Запуск из проекта-потребителя — без глобальной регистрации: в памяти проекта (MEMORY.md) лежит реестр скиллов платформы, агент резолвит путь skills/<name>/SKILL.md (монорепо — от корня репо; плагин — сиблинги; внешний проект — из node_modules/shell-kit) и читает его как промт-оркестратор.
