# UI-реворк: перевёрстка и полировка без новой операции

Референс-близнец `ui-patterns.md`. Там — выбор паттерна для операции
над сущностью; здесь — визуальный реворк: перевёрстка, полировка,
декомпозиция блока, который уже работает. Вход — кейс реворка (что
перекладываем, что нечитаемо, что дёргается). Эталон — из
`skills/PROJECT.md`; отличие от эталона допустимо и фиксируется
в решении.

## Развилка в начале

- Кейс = операция над сущностью (создать/править/удалить, права,
  персистентность) → `ui-patterns.md`.
- Кейс = перевёрстка/полировка/декомпозиция без новой операции →
  эта reference.
- Единица работы — сам компонент (несколько потребителей, shared,
  API пропсов, motion-канон) → скилл `components`.
- Смешанный кейс: операция главная — её паттерн решает
  `ui-patterns.md`, попутный реворк — отдельным пунктом плана
  и отдельной строкой приёмки, не размазывать.

## Типология

```
Что не так с блоком?
├─ Решает слишком много / данные и вёрстка слиплись
│   → ДЕКОМПОЗИЦИЯ: блок → отдельный компонент; данные внутри,
│     если это демо-инструментарий; удаление одной точкой
│     (эталон: auth/RoleHint — файл + точка рендера)
├─ Экран владеет множеством компонентов / всё в одном файле
│   → ДЕКОМПОЗИЦИЯ ЭКРАНА: страница владеет только рамкой
│     и слотами, блоки — в `components/` папки модуля, один
│     блок — один файл; повтор внутри экрана ≠ shared
│     (правила, пороги и эталон auth — классификатор
│     component-levels.md, секция «Ранги»)
├─ Перечисление нечитаемо (текст, абзацы)
│   → СТРУКТУРНЫЙ ВИД: таблица / список / чипы — по плотности
│     данных и тому, сравнивают ли строки между собой
├─ Поверхность раздувается второстепенным
│   → СХЛОПЫВАНИЕ: details / аккордеон / табы; свёрнуто по
│     умолчанию, главное — в summary (эталон: auth/RoleHint)
├─ Raw hex/px и самописное вне системы
│   → ПРИВЕДЕНИЕ К ТОКЕНАМ: цвета/размеры — design-system/
│     theme.css; самописные контролы — примитивы ui-слоя ядра
│     (Button/Card/Badge/…)
├─ Переходы дёргаются / контент прыгает
│   → MOTION-ПОЛИРОВКА: transform/opacity (не layout-свойства),
│     высотный FLIP при смене контента переменной высоты,
│     prefers-reduced-motion — мгновенная смена, первый mount
│     без анимации (эталон: useSwapAnimation в auth)
└─ Состояния дырявые (нет ошибки/фокуса/подсказки)
    → КАЧЕСТВО СОСТОЯНИЙ: §48 затронутого блока + a11y —
      aria-invalid, role="alert", autocomplete, фокус-состояния
```

## Правила

- **Уровень изменений** — по классификатору
  `prototype-to-app/references/classifiers/component-levels.md`
  (токен → примитив → блок → виджет → страница): реворк честно
  называет, до какого уровня трогает.
- Shared-подъём — только предложением, не молчаливым выносом
  (второй потребитель = кандидат, решение за планом).
- Эталоны визуальной работы — раздел «Эталоны» `skills/PROJECT.md`;
  сверяться до выбора приёма.
- `data-name` на новых/пересобранных корневых элементах обязателен.
- **Мобильная адаптация — обязательный вопрос clarify**: как блок
  живёт ниже брейкпоинтов проекта (не «исчезает ли», а «какая
  композиция вместо»).

## Приёмка

1. **DOM-пробы геометрии первичны**: ширины, переполнения
   (`scrollWidth − clientWidth`), высоты строк/блоков — числа,
   не «на глаз».
2. Скриншот + визуальная проверка — вторым проходом, поверх проб.
3. §48-аудит затронутых состояний (что блок делает в loading /
   error / empty / disabled — по мере релевантности).
4. Есть каталог компонентов (скилл `storybook`) — stories для
   пересобранного и его веток.

## Что фиксировать в решении

`тип реворка → уровень → отличие от эталона → приёмка
(пробы/состояния)` — одной строкой в решении (D-запись или док
модуля).
