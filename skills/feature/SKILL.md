# /feature

Скилл разработки: точечная доработка живого модуля — «в модуле X в месте
Y добавить операцию над объектами Z с учётом роли». Типичный вход — дыра
в ТЗ: заказчик не продумал редактирование, удаление, модерацию. Работает
по готовой декомпозиции, поэтому главный ресурс — **аналоги в самом
проекте**: если похожее уже сделано, паттерн и второй потребитель видны
сразу, вопросы сводятся к отличиям от эталона.

## A. Проектный слой (читать до любых вопросов)

1. Найди `skills/PROJECT.md` в корне проекта — нюансы проекта:
   дефолты по ролям, персистентности, эталоны («где такое уже
   сделано»), запреты. Дефолты фазы clarify берутся **оттуда и из
   аналогов**, не из воздуха.
2. Резолв скиллов каскадом: проектный слой `<проект>/skills/<skill>/`
   оверрайдит платформенный (резолв платформенного — монорепо
   `skills/<skill>/`, плагин-сиблинги, `node_modules/shell-kit`;
   контракт — `references/project-layer.md`).
3. Если проект собирался через prototype-to-app — рядом `.app-build/`
   (планы модулей, журнал D-xxx); используй их как карту.

## B. Флоу: locate → clarify → plan → implement → verify

### 1. locate — где живёт фича

- Модуль из запроса; не назван — определи по объектам/месту и спроси,
  если неоднозначно.
- Прочитай: `docs/modules/<id>/<id>.md` (если есть), контроллер, сервис,
  вьюхи, запись в реестре модулей.
- Фича межмодульная → владелец один (владелец сущности); остальным —
  маршрут или сервис владельца, прямых импортов нет.
- Найди аналог: похожая операция в соседних модулях (поиск по
  мутациям/правам/паттерну). Аналог = эталон по умолчанию; отличия
  от эталона — и есть повестка clarify.

### 2. clarify — как именно (содержательный гейт)

Вопросы по кейсу, у каждого дефолт (PROJECT.md / аналог):

- **UI-паттерн**: решающее дерево `references/ui-patterns.md`
  (модалка / inline / форма-панель / визард / отдельный экран /
  контролируемый виджет).
- **Визуальный реворк?** — кейс без операции над сущностью
  (перевёрстка/полировка/декомпозиция) → типология и приёмка
  `references/ui-rework.md`; компонент как единица работы (несколько
  потребителей, канон/motion/API) → скилл `components`.
- **Данные**: новая мутация сервиса или визуальный стейт? Персистентная
  коллекция — нужна ли и какой bump `schemaVersion` при смене схемы?
- **Права**: роль → право (none/own/any по матрице проекта; владение
  решает домен). Если право новое — куда в матрицу.
- **Состояния §48 операции**: pending («Сохраняем…» + disabled), сбой —
  ретрай на месте; доступ по роли.
- **Границы**: что НЕ входит; отложенное — в «Открытые вопросы» дока.

Гейт: представить решения таблицей «вопрос → дефолт → выбор», а не
вопрошать по одному.

### 3. plan — мини-план (в сообщении, без файла)

- Диф типов: расширение vm-union (новые режимы/поля), интерфейс
  сервиса (+мутация), доменные типы.
- Затронутые компоненты по уровням (классификатор
  `references/classifiers/component-levels.md` скилла
  prototype-to-app, резолв — project-layer.md);
  изменения в shared — только предложением.
- Диф `docs/modules/<id>/<id>.md`.

### 4. implement

Types-first в миниатюре: типы и сервис → вьюхи → клей контроллера.
Конвенции платформы и PROJECT.md обязательны; сверяйся с эталоном.
Ветвление: расширяешь тернарник за плоский (вложенность, вторая
ось, третья ветка) или гирлянду `&&` — не доращивать, а перевести
на derive-once + реестр тем же ходом (канон и эталон — PROJECT.md
проекта, «Ветвление»).

### 5. verify

- §48-аудит новой операции (каждое состояние на месте).
- Визуальная приёмка реворка (если был): DOM-пробы геометрии +
  §48 затронутых состояний (`references/ui-rework.md`).
- Сборка: typecheck / lint / build — чисто.
- Если в проекте есть каталог компонентов (скилл `storybook`) —
  stories для новых компонентов и веток vm-union.
- Дока обновлена (`docs/modules/<id>/<id>.md`), включая «Открытые вопросы».
- Решения зафиксированы: есть `.app-build/decisions.md` → D-записи
  туда; нет → раздел «Поведение» дока модуля.

## C. Правила

- **Дефолт ≠ угадывание**: гипотеза с обоснованием (аналог или
  PROJECT.md). Нет ни того ни другого — честный вопрос без дефолта.
- Не выходить за границу модуля без вопроса; shared-кандидат —
  предложение, не молчаливый вынос.
- **Малая правка сворачивается**: locate+clarify одним вопросом,
  реализация, verify сборкой — не тащить весь флоу через три строки.
- Выученный нюанс проекта (повторился дважды) — кандидат в
  `skills/PROJECT.md`; обобщившийся паттерн флоу — кандидат в правку
  этого скилла (см. `references/project-layer.md`, «подъём»).

## D. Точки роста (честно)

- Стейта на фичу пока нет — флоу линейный, живёт сессию. Если фичи
  перестанут влезать в сессию — мини-машина
  `.app-build/features/<id>/` (state + план); текущий контракт не
  против.
- `references/ui-patterns.md` — первый срез; пополняется реальными
  кейсами по мере обкатки.
- `references/ui-rework.md` — второй срез (визуальный реворк без
  операции над сущностью); пополняется реальными кейсами так же.
