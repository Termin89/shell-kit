# /product-analysis

Продуктовый анализ по коду: восстановить фактическую картину продукта —
назначение модулей, оси ролей и матрицы доступов, бизнес-кейсы (happy /
альтернативные / edge), связи модулей, разрывы — и зафиксировать её в
семействе доков `docs/modules/` по контракту
(`skills/product-analysis/references/doc-contract.md`).

Один прогон = один охват: весь продукт или один модуль. Обратная задача
(доки есть, код ушёл — переоценить) — скилл `doc-sync`. Функциональные
доки `docs/modules/<id>/<id>.md` ведёт конвейер `improvements` — этот
скилл их не трогает.

## A. Фазы (стейт-машина)

### 1. intake — вход и охват

- Сначала проектный слой: `projects/<app>/skills/PROJECT.md` (роли,
  конвенции, эталоны, запреты) — читать до вопросов, дефолты оттуда.
- Охват из запроса: **продукт** целиком | **module `<id>`** | **роль**.
  Охват задаёт состав поставки (контракт, раздел «Семейство»):
  - продукт → корневые доки `product-overview.md`, `roles.md`,
    `cases.md` (индекс), `cross-cases.md` (реестр CC-N) +
    `<id>/<id>-cases.md` на каждый модуль (раскладка — контракт §2);
  - модуль → `<id>/<id>-cases.md` + затрагиваемые секции overview/roles/cases
    (точечно, не переписывать доки целиком);
  - роль → раздел в `roles.md` + её строки в матрицах.
- Если целевые доки уже есть: это доработка семейства — дополнить
  секции; если вопрос в актуальности существующих («код поменяли») —
  вести в `doc-sync`, не в повторный анализ.

### 2. explore — сбор фактов

- **Код — единственная истина фактов**: реестр страниц
  (`src/app/modules.ts`), матрица прав (`src/app/roles.ts`), домены
  (`src/services/*`), страницы и контроллеры (`src/ui/pages/*`),
  конфиги/лимиты.
- Доки-спутники (`docs/modules/<id>/<id>.md`, comments/*.md, MEMORY-контекст
  проекта) — источник-подсказка: история решений, даты, цитаты ТЗ.
  Утверждение-факт из доки проверяется кодом; без подтверждения —
  пометка «гипотеза / требует подтверждения».
- Сбор — параллельные Explore-агенты, по одному на область (модуль или
  app-слой). Промпт каждому — с возвратом по схеме контракта:
  сущности → экраны (состав — из `views/<экран>/` модуля, fallback —
  роут-детекция контроллера) → карта «роль × view × действие ×
  доступ» → кейсы (happy/альт/edge) → не реализовано. Тщательность:
  very thorough для домена, medium для обвязки.

### 3. synthesize — сборка картины

- Приоритизация модулей: ядро / поддерживающие / вторичные — с
  обоснованием по данным проекта (доменные связи, монетизация,
  транзакции), не по объёму кода.
- Роли: эффективные оси (клубная роль × суб-роль × статус организации ×
  пер-пользовательные флаги) и сводная матрица «эффективная роль ×
  доступ» — включая гостя.
- Кейсы: happy path + альтернативные + edge («что ломается, где
  конфликты ролей, где узкие места»); сквозные сценарии через модули.
- Разрывы: реализованное не до конца / заказанное, но отсутствующее —
  отдельным блоком, без смешения с гипотезами.

### 4. gate — утверждение суждений

- Через AskUserQuestion: приоритизация модулей, состав эффективных
  ролей для сводной матрицы, структура семейства доков.
- Факты (маршруты, поля, статусы, матрицы из кода) не гейтятся.

### 5. write — запись по контракту

- Формат и хедер — `references/doc-contract.md`; хедер обязателен:
  `sources` (глобы), `verified = дата · short-sha HEAD`, `stale=false`.
- Стиль: русский, плотно, без воды; таблицы для ролей/статусов/матриц;
  пути к файлам для проверяемости; гипотезы — явной пометкой.

## B. Правила

- Не выдумывать: нет данных в проекте → «гипотеза / требует
  подтверждения» (в конце доки — отдельным блоком).
- Факт vs суждение: факт проверяем кодом и не гейтим; суждение
  (приоритет, «главный кандидат на доработку») — авторское, гейтим.
- Моки честно: заглушки «этап C», mock-конвенции, пересевы LS —
  описывать как статус реальности платформы, не как продукт.
- Персистентность: скилл только пишет доки; коммит — по запросу
  пользователя.
- Точки роста скилла: интеграция с feature (пометка stale на verify),
  новые типы доков — через изменение контракта, не через скилл.
