# Контракт доков product-docs

Единый формат семейства продуктовых доков: создаёт `/product-analysis`,
сопровождает `/doc-sync`. Живут в `docs/modules/` проекта.

## 1. Хедер-метаданные (обязателен)

Первая строка после `#`-заголовка доки — HTML-комментарий:

```
<!-- product-docs: sources=[<глобы>, …] verified=YYYY-MM-DD·<short-sha> stale=false -->
```

- `sources` — глоубы файлов-источников фактов (для git-дифа в doc-sync):
  страницы, домены, реестр, матрица прав. Например
  `sources=[src/ui/pages/feed/**, src/app/roles.ts]`.
- `verified` — дата и short-sha коммита, на котором факты проверены
  последним проходом (analysis или sync).
- `stale` — `true`, если sources менялись после `verified` и дока не
  пересмотрена (ставит doc-sync; в перспективе — feature на verify).
  Дока с `stale=true` не считается источником истины.

## 2. Семейство доков

**Раскладка по папкам**: сквозные доки — в корне `docs/modules/`;
у модуля больше одного дока → папка `docs/modules/<id>/` с сохранением
имён файлов (`<id>.md` — функциональная дока конвейера `improvements`,
`<id>-cases.md` — продуктовые кейсы этого контракта,
`<id>-memory.md` — рабочая память, прочие спутники рядом). Имена не
сокращаются: базовое имя файла остаётся уникальным по всему
`docs/modules/` и грепается из любого места.

| Дока | Тип | Скелет секций |
|---|---|---|
| `product-overview.md` | продукт целиком | резюме → приоритизация модулей + схема связей → блок на модуль (назначение / сущности / карта «роль × view» / кейсы / не реализовано) → сводная матрица ролей → сквозные выводы и разрывы → гипотезы |
| `roles.md` | модель доступа | оси ролей (схема) → где что живёт (таблица источников) → резолв при входе → механика проверок (`can`/`orgCan`/комбинированные) → матрица каждой оси → сводная «эффективная роль × доступ» (включая гостя) → кейсы комбинирования → драфты несуществующих осей |
| `cases.md` | индекс + таксономия | таксономия «модульный vs общий» (критерий отнесения) → правила исполнения (модульные параллельно / общие последовательно + заморозка связей) → таблица-индекс семейства → обвязка по ролям |
| `cross-cases.md` | общие (сквозные) кейсы | по кейсу (CC-N): суть/поток → модули и связи → заморозка → статус; правила очереди общих пулов |
| `<id>-cases.md` | модуль | роль модуля в системе → карта «роль × view» → кейсы (happy / альтернативные / edge) → не реализовано |

Функциональные `docs/modules/<id>/<id>.md` (ТЗ, поведение, открытые
вопросы) в контракт **не входят** — их ведёт конвейер `improvements`;
продуктовые `<id>-cases.md` живут в той же папке модуля.

## 3. Правила содержания

- **Код — истина фактов.** Маршруты, поля, статусы, лимиты/квоты,
  матрицы доступов, состав экранов — только из кода, с путями к файлам.
- **Карта «роль × view» — единица декомпозиции модуля.** Строки —
  view (экраны), колонки — эффективные роли, ячейка — действия роли
  на экране («—» = denied/скрыт; развилки §48 по ролям — denied/empty —
  в ячейке). Состав экранов — из структуры модуля: `views/<экран>/`
  (папка = экран = слайс контроллера = ключ vm, канон
  component-levels.md), fallback — роут-детекция контроллера. Карта
  зеркалит код: строка ↔ папка ↔ слайс ↔ ключ vm — навигация для
  человека и LLM без открытия файлов. Эквивалентные на модуле оси
  ролей схлопываются в одну колонку с оговоркой (полная развертка
  осей — roles.md).
- **Доки-спутники — подсказки** (история решений, даты, ТЗ). Факт из
  доки без подтверждения кодом → «гипотеза / требует подтверждения».
- **Факт vs суждение.** Суждения (приоритизация, сквозные выводы,
  «главный кандидат на доработку») — авторские: помечаются как выводы,
  при пересмотре меняются только через гейт (правило doc-sync).
- **Моки — статус реальности**: заглушки «этап C», mock-конвенции,
  пересевы LS — фиксируются как состояние платформы, не продукта.
- **Общие кейсы — единственная точка изменения межмодульных связей.**
  Пока CC-кейс открыт или стабилен, его заморозки (deep-link, intent,
  kind-ы уведомлений, владение/авторство, контракты сервисов) не
  меняются модульными доработками — связь меняется вместе с кейсом
  одним ходом.
- Стиль: русский, плотно, таблицы для ролей/статусов/матриц, без воды.

## 4. Жизненный цикл маркера

- `product-analysis` (создание/расширение): пишет `verified =
  сегодня · short-sha HEAD`, `stale=false`.
- `doc-sync` (переоценка): диф по `sources` от `verified`-sha → правки
  фактов + гейт суждений → `verified = сегодня · sha HEAD`, `stale=false`.
  Незакоммиченные изменения — в отчёт с пометкой, в `verified` не
  попадают.
- Дока без хедера — легаси: либо прогнать product-analysis (установка
  контракта), либо добавить хедер вручную и пометить `stale=true`.
