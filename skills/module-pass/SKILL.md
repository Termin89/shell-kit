# /module-pass

Параллельный плановый проход по модулям: один запуск — по суб-агенту
на модуль, каждый ведёт свой модуль через полный проход (структура →
аудит → L2 → доки) с обязательной верификацией. Оркестратор держит
таск-лист, принимает верификацию как гейт статуса, коммитит
пер-модульно и сдаёт сводную таблицу. Эталон прохода — фид u-kon
(2026-09-27, docs/modules/feed/feed-memory.md).

## Модель

- **Оркестратор** (этот агент): intake → таски → спавн волной → приём
  отчётов → глобальная верификация → пер-модульные коммиты → сводный
  статус. Единственный, кто трогает таск-лист и git-мутации.
- **Суб-агент** (general-purpose): один модуль по playbook
  (`references/playbook.md`), изолированный порт, своя страница
  браузера. Не коммитит, не лазит в чужие модули и общий таск-лист;
  ошибки tsc/oxlint чужих файлов (WIP соседей по волне) игнорирует.

## Режимы запуска

Режим задаётся запросом; дефолт — ask.

- **ask** — спрашивать: решения через гейты (перечень модулей/фаз,
  грязное дерево, дыры аудита с развилкой чинки, суждения). Вопросы
  задаёт только оркестратор — суб-агенты пользователя не видят,
  в возврате отдают только факты и варианты.
- **full** — «без вопросов» / «полный доступ»: гейты сняты, оркестратор
  не спрашивает вообще — решения по канону PROJECT.md и дефолтам
  playbook, каждое суждение помечается в сводке «решение оркестратора
  — пересмотреть». Ход прогона виден этапами в обоих режимах: статусы
  тасков + короткая строка на волну. Режим не снимает безопасность:
  WIP пользователя не трогать, destructive-git нет, пуш — по просьбе.

## A. Фазы оркестратора

### 1. intake

- Сначала проектный слой: `projects/<app>/skills/PROJECT.md` (канон,
  эталоны, запреты) — дефолты оттуда.
- Состав модулей — из `src/ui/pages/*` (папка = модуль). Из запроса
  вычесть прошедших: модуль, чей `docs/modules/<id>/<id>-memory.md`
  фиксирует завершённый плановый проход, по умолчанию пропускается.
- `git status`: грязное дерево — ask: спросить (чей WIP / незакрытые
  пачки — коммитить до прогона или исключить модули); full: продолжать,
  грязные файлы считать WIP пользователя — в списки «не трогать» и в
  сводку. WIP-файлы внутри модулей — агентам в промпт списком
  «не трогать».
- Перечень: запрос уже задал список модулей/фаз — не переспрашивать
  (в обоих режимах); иначе ask — короткое подтверждение (модули ×
  фазы), full — идти по выведенному автоматически.

### 2. таски

- TaskCreate на каждый модуль: «Прогон <id>» (в описании — фазы и
  определение готовности). Статус переводит только оркестратор:
  in_progress на спавне, completed — после принятой верификации.

### 3. спавн (волны)

- До спавна поднять один dev-browser-сервер (skill dev-browser:
  `server.sh` из базовой папки скилла, ждать Ready) — агенты
  подключаются клиентом.
- Волна ≤ 3–4 агентов (каждый поднимает свой vite-порт). Task-вызовы
  одной волны — одним сообщением; порт и имя страницы оркестратор
  выдаёт в промпте (порт 3010+i, страница `pass-<id>`).
- Промпт агенту: модуль и его путь, фазы, выданный порт, «прочитай
  skills/module-pass/references/playbook.md и PROJECT.md», схема
  отчёта, запреты (git-мутации, таск-лист, чужие модули, WIP-файлы).

### 4. приём

- TaskOutput по агентам волны. Отчёт без верификации или с дырами →
  resume агента на доработку или доработка оркестратором; таска не
  закрывается. Следующая волна — после приёма предыдущей.
- **Права**: агент (или сам оркестратор — Task-вызов, команда, запись)
  упёрся в запрет — это раздел отчёта «права»: какого права не хватило
  и на чём споткнулся. Оркестратор собирает блокировки в сводку и либо
  выполняет действие сам, либо явно просит пользователя выдать права.
  Молча проглоченная блокировка — дефект отчёта.

### 5. closeout

- Глобально один раз (агенты проверяли только свои файлы): `npx tsc
  -p tsconfig.app.json --noEmit`, `npx oxlint projects/<app>/src`,
  сборка — в монорепо `PROJECT_APP=<app> npx vite build` из корня,
  в репо проекта `npm run build`. Хвосты чинит оркестратор.
- Коммиты пер-модульные, последовательно (файлы модулей не
  пересекаются): `<app> <id>: плановый проход (структура/аудит/L2/доки)`.
- Сводная таблица: модуль × фазы × вердикт + риски/хвосты; таски →
  completed. Пуш — только по явной просьбе.

## B. Правила

- Поведение неизменно: структурная фаза — DOM-пробы побайтово до/после;
  новые фичи — не этот скилл, а /feature.
- Верификация — гейт статуса: без чистых tsc/oxlint по своим файлам и
  браузерных проб (состояния §48, data-name, клавиатура, mobile 390)
  модуль не закрывается.
- Изоляция данных: порт на агента (LS-моки одного origin не
  пересекаются), страница `pass-<id>`; после смоуков агент перечищает
  свои LS-ключи.
- Спутники внутри прохода (агенты читают их как текст, не Skill):
  канон структуры — `skills/prototype-to-app/references/classifiers/
  component-levels.md`; полировка/L2 — `skills/components/SKILL.md`;
  конвенция доков — `docs/modules/` проекта.
