# Playbook: расщепление монолита service.ts

Процедура декомпозиции выросшего `service.ts` на канон
`types/seeds/mock/api/service` (см. SKILL.md §2–3). Главный инвариант:
**чистый перенос** — логика, идентификаторы, тексты, порядок строк
внутри файлов не меняются; меняется только раскладка по файлам и
импорты. Эталон результата — репо u-kon (github.com/Termin89/u-kon),
`src/services/organizations/`.

## Порядок

1. **Read монолита целиком.** Определи по факту состав: какие
   константы — сиды (демо-данные), какие — контракт (квоты, дефолты),
   какие — приватные для мока (подписи статусов для аудита). Точный
   состав файлов уточняется по факту — канон допускает опускание
   пустых (нет сидов → нет seeds.ts).
2. **Write `types.ts`** — контракт: сущности, ошибки, константы-квоты,
   `interface XService` с док-комментариями. Хедер-файл: что за домен,
   ссылки на доки, «здесь только контракт; реализации — mock.ts /
   api.ts, демо-данные — seeds.ts, сборка — service.ts».
3. **Write `seeds.ts`** — демо-данные: SEEDS/MEDIA_SEED, фабрики
   (`seedsAll`), мок-URL документов, `toRecord`-развёртка компактных
   сидов. Импорт из types.ts — только типы и публичные константы.
   Если сидов нет — файл не создаётся, пустые коллекции мока остаются
   фабриками `() => []` в mock.ts.
4. **Write `mock.ts`** — класс стратегии: конструктор PersistentMock
   (schemaVersion + история версий схемы комментарием), приватные
   хелперы и гварды, продюсер уведомлений, все методы интерфейса.
   Приватные константы мока (например `PARTNER_STATUS_LABELS`)
   переезжают сюда и не экспортируются.
5. **Write `api.ts`** — если api-стратегии не было вовсе (аномалия
   канона): заглушка, все ручки бросают `NOT_CONNECTED("<что>")`,
   класс implements XService. Если была — перенос как есть.
6. **Write `service.ts`-barrel** (старый монолит удалить — см.
   грабли №1): `defineService<XService>` со стратегиями mock → api,
   `export * from "./types"`, синглтон `<id>Service`. Хедер-комментарий:
   домен, app-wide/page-local rationale, структура папки, стратегии.
7. **Правка импортов потребителей.**
   - App-wide: вход `services/<id>/service` **не меняется** — файл
     остался на месте, потребители не трогаем.
   - Page-local: монолит `<page>/service.ts` стал папкой
     `<page>/service/`, вход — `<page>/service/service.ts`. Импорты
     `./service` → `./service/service`, `../service` →
     `../service/service` и т.д. **Включая кросс-страничные**
     (например feed → messenger: `../../messenger/service` →
     `../../messenger/service/service`) — ищи grep'ом по всему src.
   - Сопутствующие файлы сервиса (например `session/storage.ts`)
     правят импорт `./service` → `./service/types` (им нужен только
     контракт) либо `./service/service` — по факту использования.
8. **Верификация** — конвейер не идёт дальше при ошибке:
   `tsc` (см. грабли №2) → `npx oxlint projects/<app>/src` →
   сборка (монорепо — `npm run project:<app>:build`, репо
   проекта — `npm run build`). Контроль границ: `wc -l` по новым
   файлам — сопоставимо с монолитом (сумма ≈ строки монолита +
   хедеры/импорты).

## Грабли

1. **ts/tsx-неоднозначность имён.** Пока старый `<page>/service.ts`
   не удалён, рядом лежит и файл, и папка `service/`: резолв
   `./service` неоднозначен (файл выигрывает, правки импортов «не
   работают»). Удаляй монолит в момент появления barrel.
2. **tsconfig в корне репо, вывод — в файл.** Монорепо: tsconfig.app.json
   лежит в корне shell-kit, а не в проекте. Команда из корня репо:
   `npx tsc -p tsconfig.app.json --noEmit > /tmp/tsc.txt 2>&1;
   echo code=$?` — без redirect длинный вывод рвёт контекст агента;
   код завершения проверяй именно так (pipe съедает exit code).
3. **Публичная поверхность не расширяется.** Расщепление — не
   рефакторинг API: ничего не переименовывать, не «улучшать»,
   приватные константы не экспортировать. Диф монолита и суммы новых
   файлов должен показывать перенос, а не переписывание.
4. **`export *` и коллизии.** Barrel реэкспортирует types.ts целиком;
   если в монолите что-то экспортировалось из середины реализации —
   переноси в types.ts только если это контракт. Случайные экспорты
   хелперов (pluralRu и т.п., которые едят вьюхи) остаются
   экспортированными из того файла, где живут.
5. **Порядок док-хедеров.** Каждый новый файл открывается
   док-комментарием (как в эталоне organizations): назначение файла
   и его место в структуре — читатель папки понимает раскладку без
   открытия SKILL.md.

## Доки после прохода

- Короткая строка о структуре в module-доках (`docs/modules/<id>/
  <id>.md`), где они есть.
- Одна сводная запись в `<id>-memory.md` затронутых модулей.
- Реестр скиллов / памяти проекта — если проход массовый (все
  сервисы), одной сводной записью в MEMORY.md.
