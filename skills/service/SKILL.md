# /service

Скилл структуры доменных сервисов: как выглядит правильный сервис, что
кладётся в какой файл и почему. Вход типовой: «создай сервис X» (новый
домен) либо «расщепи service.ts» (монолит вырос). Эталон реализации —
репо u-kon (github.com/Termin89/u-kon):
`src/services/organizations/` (расщеплён 2026-09-28);
эталон можно показывать пользователю как образец.

## 1. Семантика: сервис = суррогат бэкенда

Приложение живёт на моках до этапа C (транспорт SmartyPro). Сервис —
это **бэкенд-суррогат**: у настоящего бэкенда домен выглядел бы именно
так. Отсюда два следствия.

- **Контроллер — форма вьюхи, сервис — форма бэкенда.** Контроллер
  (`module.ts` + `controllers/`, `vm.ts`) говорит на языке экрана
  (загрузка, стейт-машина вьюхи, presentation-данные для вью); сервис
  говорит на языке домена (сущности, инварианты, мутации, ошибки).
  Смешение их в одном файле — запах: стейт вьюхи утаскивает доменные
  правила в слой UI, а домен обрастает concern'ами экрана.
- **Мок — честный «сервер»**: гварды инвариантов живут в mock.ts
  (вторая линия после валидации UI — как сервер отклонил бы запрос),
  уведомления — побочный эффект мутаций, персистентность и пересев —
  PersistentMock. Писать «по-настоящему» станет нечем, когда api.ts
  займёт место mock.ts: контракт (types.ts) и правила (mock.ts) уже
  разделены.

**Размещение.** App-wide сервис (`src/services/<id>/`) — домен нужен
больше чем одной странице или ядру (сессия, уведомления, ресурсы,
организации: профиль + каталог + админка). Page-local
(`src/ui/pages/<id>/service/`) — домен живёт внутри одной страницы,
наружу не нужен (лента, мессенджер, заявки). Сомневаешься — page-local:
поднять проще, чем опустить (подъём = перенос папки + правка путей).

## 2. Структура: 4+1 файл по швам изменений

```
<serviceDir>/                 # app-wide: src/services/<id>/
                               # page-local: src/ui/pages/<id>/service/
├── types.ts    # контракт: сущности, ошибки, константы-квоты, interface XService
├── seeds.ts    # (опц.) демо-данные: SEEDS/MEDIA_SEED/фабрики коллекций
├── mock.ts     # стратегия mock: PersistentMock|in-memory, schemaVersion
│               # (+история версий схемы комментарием), гварды,
│               # продюсер уведомлений
├── api.ts      # стратегия api: заглушка NOT_CONNECTED (этап C)
└── service.ts  # сборка defineService({mock, api}) + `export * from "./types"`
                # — единственный публичный вход
```

**Канон опциональности.** Обязательны types / mock / api / service;
seeds.ts — опционален. Нет сидов — файла нет: коллекции объявляются
ленивыми (`collections: { items: () => [] }`), записи создаёт первая
мутация, а не пересев. Так живут сервисы-события u-kon —
notifications (записи создают продюсеры доменных событий), а также
permissions, settings, applications — все без seeds.ts. Отступление
по api.ts — только осознанное: внутреннему сервису без внешних
ручек заглушка не нужна, но канон предпочитает иметь её всегда —
расщепление feed → messenger показало, что отсутствие api.ts —
аномалия.

**Доп. файл допустим, когда забота отделима** от четырёх ролей:
`session/storage.ts` — LS-механика сессии отдельным статичным
импортом (App берёт токен, не утаскивая сервис в eager-чанк);
`messenger/service/seedMedia.ts` — генерация блобов сид-вложений
(транслитерация, мини-PDF). Доп. файл живёт рядом, не переезжает и
не становится вторым публичным входом — потребители идут через
service.ts (storage.ts — осознанное исключение: он и есть точка
статичного импорта).

Почему именно эти швы — они независимы в изменениях:

| Файл | Что меняется независимо от остальных |
|---|---|
| types.ts | контракт и сущности (реакция на ТЗ; API-контракт этапа C) |
| seeds.ts (опц.) | демо-данные (реакция на демонстрационные сценарии) |
| mock.ts | правила и схема хранения (schemaVersion, гварды) |
| api.ts | транспорт (этап C: замена заглушек на REST-клиент) |
| service.ts | сборка стратегий (флаги моков, порядок резолва) |
| доп. файл | отделимая забота: storage-механика, генерация медиа |

Схема, сид-данные, правила и транспорт меняются в разное время по
разным причинам — расщепление кладёт каждый тип изменений в свой файл,
ревью и дифы становятся точечными.

## 3. Правила содержимого

- **types.ts — только контракт.** Сущности (`Record`/`Data`/`Version`),
  union-типы статусов, классы ошибок домена (`XError extends Error`,
  name + префикс `[<id>]` в сообщении, `readonly code` из union-кода —
  контроллер показывает баннер по коду, не парсит текст; эталон
  `OrgQuotaError` → баннер в партнёрской админке), константы-квоты
  (единый источник для UI и мока), `interface XService` — все публичные
  методы с док-комментариями. Никакой реализации. Публичная поверхность
  минимальна: то, что реально потребляют контроллеры/вьюхи.
- **seeds.ts — только данные.** `SEEDS` (массив записей или компактный
  формат + `toRecord`-развёртка), `MEDIA_SEED` (медиа-реестр для
  IndexedDB), фабрики коллекций (`seedsAll()`), мок-URL реальных
  публичных документов. Импортирует из types.ts только типы и
  фолбэк-константы. Потребитель — mock.ts (пересев).
- **mock.ts — правила.** Класс `XMockService extends PersistentMock
  implements XService`: `schemaVersion` с историей версий схемы
  комментарием в конструкторе (v2: …; v3: …), коллекции-фабрики,
  гварды инвариантов (квоты, единственность, статусы), уведомления —
  **побочный эффект мутаций** через `notificationsService.push` с
  детерминированными id (дедуп) и fire-and-forget (`void …catch(() => {})
  `): провал уведомления не роняет операцию. Приватные константы
  (подписи статусов для аудита и т.п.) остаются здесь, наружу не
  идут. In-memory мок (без PersistentMock) допустим для лёгких
  сервисов — но schemaVersion тогда не нужен. Семантика ядра
  (резолв per-call, MockList-контракт, пересев) —
  `references/persistent-mock.md`.
  **Рост mock.ts** — тот же порог ~400–500 строк, что и у монолита:
  крупнейшие моки u-kon (requests 1368, feed 810, messenger 650)
  уже переросли. Выносится файлом рядом, мок-локальный и не часть
  контракта: аудитор (журнал мутаций), продюсер уведомлений
  (kind-словарь, фабрики id), id-фабрики. Доменные ошибки —
  наоборот, в types.ts (§ выше: их потребляет контроллер).
- **Актёр мутаций.** Мутации, оставляющие след «кто сделал»,
  принимают актора параметром — `{ name, email }` (`OrgActor`,
  `RequestActor`): контроллер берёт пользователя из сессии, мок
  сессию сам не читает. Снапшот актора пишется в запись / версию /
  журнал аудита (автор заявки, автор версии организации), а не
  только в лог мока.
- **Id-фабрики.** Две роли идентификаторов (эталон requests):
  технический uid — время-сортируемый, без координации
  (`req_${Date.now().toString(36)}${6 случайных base36}`);
  человекочитаемый номер — max+1 по коллекции (`REQ-0NNN`,
  `nextRequestNumber`). Оба иммутабельны после создания; на этапе C
  uid подменится серверным, номер останется клиентским соглашением.
- **Продюсер уведомлений.** Внутри мутации — приватный хелпер
  `notify(input)` → `void notificationsService.push(input)
  .catch(() => {})`: fire-and-forget, провал пуша не роняет
  операцию. Id события детерминированный
  (`<kind>-<сущность>-<адресат>`, напр. `org-status-<orgId>-
  published`): повтор события обновляет запись, а не дублирует
  (put = upsert). Kind — из словаря `AppNotificationKind` сервиса
  notifications; меняешь набор kind'ов или формат id — проверь
  schemaVersion notifications (пересев вычищает осиротевшие записи).
- **Write-through → перечитка.** Мутация пишет в LS и возвращает
  результат, но не патчит стейт страницы: потребитель перечитывает
  через `getQueryPort().invalidate(["<service>"])`. Кеш-ключи
  запросов — с общим префиксом (`["requests", "list"]`,
  `["requests", "request", id]`): одна инвалидация по префиксу
  кроет списки, детальные и производные выборки.
- **Кросс-сервисные импорты** разрешены двух видов: lookup
  метаданных (resources → organizations; session → applications,
  organizations; notifications → settings на чтении; requests →
  messenger, organizations) и продюсер уведомлений (все домены →
  notifications). Запрещены циклы рантайм-импортов (замыкание на
  живые значения); тип-импорт в обратную сторону допустим
  (applications/types ← session). Страницы друг друга не
  импортируют — только сервисы.
- **Сайд-эффекты чтения** в моке допустимы и идемпотентны:
  публикация scheduled-записей с наступившим publishAt при чтении
  ленты (feed), самоисцеление битых ссылок (`healChat` в requests —
  пересев мессенджера снёс чат, чтение восстанавливает его).
  Честный суррогат сервера делает на чтении то, что делал бы
  сервер: исполняет расписания, чинит ссылки.
- **api.ts — заглушка.** Все ручки бросают `NOT_CONNECTED("<что>")` —
  безусловный fallback-стратегия: реальный клиент появится вместе с
  transport (этап C), маппинг эндпойнтов — в доке модуля.
- **service.ts — сборка.** `defineService<XService>` со стратегиями
  mock (флаг `ctx.mockFlags.<id>`) → api (`available: () => true`),
  `export * from "./types"` и экспорт синглтона `<id>Service`.
  Хедер-комментарий: что за домен, почему app-wide/page-local,
  структура папки, стратегии. **Единственный публичный вход**:
  потребители импортируют `services/<id>/service` (app-wide) или
  `./service/service` (page-local) — внутренние файлы никто не
  импортирует напрямую.

## 4. Порог расщепления

Монолит режется при ~400+ строках или заметных сидах (сотни строк
демо-данных в середине файла мешают читать правила). Мелкий сервис
может оставаться одним файлом до роста — но по явному решению все
сервисы u-kon приведены к канону (единая структура важнее экономии
файлов). Новый сервис пишется сразу по канону — стоимость нулевая,
вопрос «когда резать» не возникает. Выросший mock.ts режется по тому
же порогу — куда выносить, см. §3 («Рост mock.ts»).

## 5. Процедура

- Новый сервис: структура §2, правила §3, регистрация флага мока в
  App.tsx (mockFlags) при необходимости; после создания — аудит-карточка
  (`references/service-audit.md`), дыры — в открытые вопросы.
- Расщепление существующего монолита: см.
  `references/playbook.md` — перенос без изменения логики, barrel,
  правка импортов потребителей, верификация tsc/oxlint/build.
- Dev-тула стратегий (shell-kit ≥ 0.4.0): `defineDev` (subpath
  `shell-kit/devtools`) — плавающая кнопка «DEV» → панель «API ·
  Сервисы»: все сервисы реестра (`getServiceCatalog`; доступные
  стратегии — недоступные, `available: false` (api-заглушки до
  подключения backend), не показываются, v0.4.1), радио
  mock/api, «Применить» = override в LS (`<project>:dev:strategy`)
  + reload. Точка монтирования — корень App за `import.meta.env.DEV`
  (прод-вырезание одной строкой), `applyDevStrategyOverrides()` —
  module scope до первого обращения к сервисам; dev-чанк статически
  импортирует service-модули (реестр видит только загруженное).
  Семантика реестра и override — `references/persistent-mock.md`.

## 6. Аудит

При ревью существующего сервиса («проверь сервис»), после
расщепления и после создания нового — аудит-карточка по осям
`references/service-audit.md` (✓ есть / ✗ нет / — не применимо):
персистентность, кеш-контракт, гварды, нотификации, актёры/
владение, api-стаб, медиа, связи, сидирование. Карточка фиксирует
фактическое состояние; чинится релевантное запросу, остальные дыры —
в открытые вопросы. Эталон по максимуму осей — requests (u-kon):
аудит-журнал, id-фабрики, нотификации, самоисцеление.

## D. Точки роста (честно)

- **Транспорт (этап C)**: api.ts — заглушки NOT_CONNECTED; реальный
  REST-клиент SmartyPro не обкатан — мок-паттерны (продюсер
  уведомлений, инвалидации, актёры) предстоит отзеркалить в
  transport-слое. WS-пуш событий (серверные уведомления без
  продюсера в мутации) не моделируется вовсе.
- **Курсорная пагинация**: списки отдаются целиком; контракт
  порций/курсоров появится вместе с реальным API.
- **Серверный batch**: мутации поштучны; накопление и отправка
  очередью (offline) — за рамками канона.
- **GC медиа-блобов**: MediaRef может делиться между записями;
  сборка мусора в IndexedDB вне мока — хука нет, чистит только
  пересев по префиксу сервиса.
- **Heartbeat/старение локов**: конкурентные мутации нескольких
  вкладок не моделируются (LS-конфликты не разруливаются).
- **Справочник форматов id**: `req_*`, `REQ-0NNN`, `v<N>` версий,
  ключи событий — рассыпаны по сервисам, общего реестра форматов нет.
- `references/service-audit.md` — первый срез осей (9); карточка
  примера живого сервиса обновится после первого реального прогона.
