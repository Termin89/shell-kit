# /service

Скилл структуры доменных сервисов: как выглядит правильный сервис, что
кладётся в какой файл и почему. Вход типовой: «создай сервис X» (новый
домен) либо «расщепи service.ts» (монолит вырос). Эталон реализации —
репо u-kon (github.com/Termin89/u-kon):
`src/services/organizations/` (расщеплён 2026-09-28);
эталон можно показывать пользователю как образец.

## 1. Семантика: сервис = суррогат бэкенда

Приложение живёт на моках до этапа C (транспорт SmartyPro). Сервис —
это **бэкенд-суррогат**: у настоящего бэкенда домен выглядел бы именно
так. Отсюда два следствия.

- **Контроллер — форма вьюхи, сервис — форма бэкенда.** Контроллер
  (`module.ts` + `controllers/`, `vm.ts`) говорит на языке экрана
  (загрузка, стейт-машина вьюхи, presentation-данные для вью); сервис
  говорит на языке домена (сущности, инварианты, мутации, ошибки).
  Смешение их в одном файле — запах: стейт вьюхи утаскивает доменные
  правила в слой UI, а домен обрастает concern'ами экрана.
- **Мок — честный «сервер»**: гварды инвариантов живут в mock.ts
  (вторая линия после валидации UI — как сервер отклонил бы запрос),
  уведомления — побочный эффект мутаций, персистентность и пересев —
  PersistentMock. Писать «по-настоящему» станет нечем, когда api.ts
  займёт место mock.ts: контракт (types.ts) и правила (mock.ts) уже
  разделены.

**Размещение.** App-wide сервис (`src/services/<id>/`) — домен нужен
больше чем одной странице или ядру (сессия, уведомления, ресурсы,
организации: профиль + каталог + админка). Page-local
(`src/ui/pages/<id>/service/`) — домен живёт внутри одной страницы,
наружу не нужен (лента, мессенджер, заявки). Сомневаешься — page-local:
поднять проще, чем опустить (подъём = перенос папки + правка путей).

## 2. Структура: 5 файлов по швам изменений

```
<serviceDir>/                 # app-wide: src/services/<id>/
                               # page-local: src/ui/pages/<id>/service/
├── types.ts    # контракт: сущности, ошибки, константы-квоты, interface XService
├── seeds.ts    # демо-данные: SEEDS/MEDIA_SEED/фабрики коллекций/мок-константы
├── mock.ts     # стратегия mock: PersistentMock|in-memory, schemaVersion
│               # (+история версий схемы комментарием), гварды,
│               # продюсер уведомлений
├── api.ts      # стратегия api: заглушка NOT_CONNECTED (этап C)
└── service.ts  # сборка defineService({mock, api}) + `export * from "./types"`
                # — единственный публичный вход
```

Файл без содержимого **опускается** (нет сидов → нет seeds.ts; нет
смысла в api-заглушке для внутреннего сервиса — можно опустить, но
канон предпочитает иметь: расщепление feed → messenger показало, что
отсутствие api.ts — аномалия). Сопутствующие технические файлы живут
рядом и не переезжают (пример: `session/storage.ts` — статичный
импорт для eager-чанка).

Почему именно эти швы — они независимы в изменениях:

| Файл | Что меняется отдельно от остальных |
|---|---|
| types.ts | контракт и сущности (реакция на ТЗ; API-контракт этапа C) |
| seeds.ts | демо-данные (реакция на демонстрационные сценарии) |
| mock.ts | правила и схема хранения (schemaVersion, гварды) |
| api.ts | транспорт (этап C: замена заглушек на REST-клиент) |
| service.ts | сборка стратегий (флаги моков, порядок резолва) |

Схема, сид-данные, правила и транспорт меняются в разное время по
разным причинам — расщепление кладёт каждый тип изменений в свой файл,
ревью и дифы становятся точечными.

## 3. Правила содержимого

- **types.ts — только контракт.** Сущности (`Record`/`Data`/`Version`),
  union-типы статусов, классы ошибок домена (`XError extends Error`,
  name + префикс `[<id>]` в сообщении), константы-квоты (единый
  источник для UI и мока), `interface XService` — все публичные методы
  с док-комментариями. Никакой реализации. Публичная поверхность
  минимальна: то, что реально потребляют контроллеры/вьюхи.
- **seeds.ts — только данные.** `SEEDS` (массив записей или компактный
  формат + `toRecord`-развёртка), `MEDIA_SEED` (медиа-реестр для
  IndexedDB), фабрики коллекций (`seedsAll()`), мок-URL реальных
  публичных документов. Импортирует из types.ts только типы и
  фолбэк-константы. Потребитель — mock.ts (пересев).
- **mock.ts — правила.** Класс `XMockService extends PersistentMock
  implements XService`: `schemaVersion` с историей версий схемы
  комментарием в конструкторе (v2: …; v3: …), коллекции-фабрики,
  гварды инвариантов (квоты, единственность, статусы), уведомления —
  **побочный эффект мутаций** через `notificationsService.push` с
  детерминированными id (дедуп) и fire-and-forget (`void …catch(() => {})
  `): провал уведомления не роняет операцию. Приватные константы
  (подписи статусов для аудита и т.п.) остаются здесь, наружу не
  идут. In-memory мок (без PersistentMock) допустим для лёгких
  сервисов — но schemaVersion тогда не нужен.
- **api.ts — заглушка.** Все ручки бросают `NOT_CONNECTED("<что>")` —
  безусловный fallback-стратегия: реальный клиент появится вместе с
  transport (этап C), маппинг эндпойнтов — в доке модуля.
- **service.ts — сборка.** `defineService<XService>` со стратегиями
  mock (флаг `ctx.mockFlags.<id>`) → api (`available: () => true`),
  `export * from "./types"` и экспорт синглтона `<id>Service`.
  Хедер-комментарий: что за домен, почему app-wide/page-local,
  структура папки, стратегии. **Единственный публичный вход**:
  потребители импортируют `services/<id>/service` (app-wide) или
  `./service/service` (page-local) — внутренние файлы никто не
  импортирует напрямую.

## 4. Порог расщепления

Монолит режется при ~400+ строках или заметных сидах (сотни строк
демо-данных в середине файла мешают читать правила). Мелкий сервис
может оставаться одним файлом до роста — но по явному решению все
сервисы u-kon приведены к канону (единая структура важнее экономии
файлов). Новый сервис пишется сразу по канону — стоимость нулевая,
вопрос «когда резать» не возникает.

## 5. Процедура

- Новый сервис: структура §2, правила §3, регистрация флага мока в
  App.tsx (mockFlags) при необходимости.
- Расщепление существующего монолита: см.
  `references/playbook.md` — перенос без изменения логики, barrel,
  правка импортов потребителей, верификация tsc/oxlint/build.
