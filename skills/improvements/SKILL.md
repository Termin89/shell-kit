# /improvements

Конвейер доработок модуля: обсудили кейсы → зафиксировали пул →
этап за этапом → браузерный прогон по демо-кейсам → вердикт
готовности. Один прогон конвейера = один модуль. Отдельная фича
без пула — скилл `feature`; новое приложение из прототипа —
`prototype-to-app`.

## A. Фазы

### 1. intake — обсудить кейсы

- Источники: ТЗ/письмо заказчика, боль от прошлого прогона, дыры
  состояний (§48), вопросы «а как должно вести себя, если…».
- Фиксация — `docs/Доработки/<module>.md`: по областям, а не по
  экранам (создание / редактирование / права / лимиты /
  уведомления / админка). Требования — с цитатами источника;
  спорное — помечать, не решать молча.
- Каждая область = будущий этап. Открытые вопросы — отдельным
  блоком в конце пула.

### 2. plan — декомпозиция и утверждение

- Этапы группируются волнами **от фундамента**: домен/данные →
  основной UX → вспомогательные виджеты и уведомления →
  админка/управление. Волна не начинается, пока не закрыта
  предыдущая.
- Этап атомарен: поставка имеет смысл сама по себе (компилируется,
  проверяется, не ломает остальное). Нумерация `N.M` (волна.этап).
- Гейт: пул целиком утверждается пользователем; дата утверждения
  и структура этапов — в рабочую память модуля.

### 3. execute — этап за этапом

- Каждый этап — флоу `feature`: locate → clarify (гейт-таблицей
  «вопрос → дефолт → выбор») → plan → implement → verify.
- Коммит на этап: `<project> <module>: этап N.M — суть` с полным
  сообщением (что вошло, границы, что отложено).
- Доки-спутники ведутся по ходу: функциональная
  `docs/modules/<id>/<id>.md` (цель/цитаты ТЗ/поведение/открытые
  вопросы) и рабочая память `docs/modules/<id>/<id>-memory.md`
  (статус, точки входа, как проверять, грабли, WIP-файлы
  пользователя — не трогать).
- Этап закрыт = verify зелёный (typecheck / lint / build + браузер
  по сценарию этапа) и закоммичен.

### 4. accept — приёмка по демо-кейсам

- Демо-сценарий `docs/demo/<id>.md`: «что это» на 30 секунд,
  кейсы по ролям проекта (обычно просмотр / автор / админ),
  сквозные кейсы через роли, чек-лист перед демо (учётки, чистые
  LS-ключи, заготовки данных, границы мока — что «придёт с API»,
  не показывать и не обещать).
- Прогон в браузере по ролям; каждый кейс — проверка состояния
  (DOM-проба или осознанный скриншот). Косяк → фикс → перепрогон
  кейса.
- Вердикт в memory модуля и в статус проекта: «модуль готов,
  осталась связка с API (транспорт)». Что осталось — списком:
  REST/WS, email-уведомления, серверные фичи, которых нет в моке.

## B. Правила браузерного прогона (dev-browser)

- Персистентные ключи чистить **до** загрузки приложения:
  удалить LS-ключи → потом goto. Чистка на загруженной странице
  без reload даёт смесь старых и пересеянных данных.
- Расхождение «вижу ≠ ожидаю» → сначала DOM-проба (`evaluate`:
  заголовки, стейт, ссылки), скриншоты вторичны: пайплайн
  скриншотов может лагать/кэшировать.
- Мобильный вьюпорт: окно клампится по ширине — честные размеры
  через CDP `Emulation.setDeviceMetricsOverride` и обязательно
  `clearDeviceMetricsOverride` после. После CDP-эмуляции
  доверенные клики могут промахиваться (рассинхрон вьюпортов) —
  продолжать на **новой именованной page**.
- Смена роли: удалить session-ключ + goto (перелогин), а не
  «переоткрыть». Двух-ролевые кейсы (lock, модерация, квоты) —
  второй именованный page.
- Скачивание/внешние ссылки — проверять фактом (download/popup
  event), не наличием кнопки.

## C. Связь с другими скиллами

- `feature` — исполнение одного этапа (improvements — зонт над
  пулом).
- `storybook` — verify этапа пополняет каталог компонентами/ветками.
- `production` — осознанные моки пула фиксируются в скорборде
  прод-готовности.
- `deploy` — демо-стенд для показа заказчику после accept.

## D. Границы

- Пул доработок ≠ редизайн: смена визуального языка — отдельный
  design-system конвейер. Точечный визуальный реворк внутри этапов
  (перевёрстка/полировка/декомпозиция без смены языка) — норма
  пула: флоу `feature`, типология и приёмка —
  `skills/feature/references/ui-rework.md`.
- Accept не заменяет приёмку заказчика: вердикт «готов» — про
  соответствие пулу и демо-кейсам, финальное слово за ним.
